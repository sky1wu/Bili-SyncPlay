# 运行时不变量

以下规则没有任何类型、lint 或测试能独立保证，每一条都是某个 bug 或某轮漫长复审用代价换来的。
[AGENTS.md](../../AGENTS.md) 收录每条规则的一句话版本；本文收录背后的推导——那才是你动这些代码之前需要读的部分。

改动后台播放计时、共享归属、共享运行时存储、房间事件广播或后台定时任务之前，请先读对应章节。

英文版见 [invariants.md](./invariants.md)。

## 播放计时不变量（Playback timing invariants）

其中三条在 #210 上合计花掉四轮复审。类型系统对它们一概无能为力，所以每当某条后台路径触及房间状态或播放计时时，都必须人工核对。

- **绝不用服务端时刻减本地时刻。** `serverTime` 属于服务端的钟，本地时刻属于本机的钟。两者之差是钟差，
  它不是时长，而且会自行漂移——接收端拿它当目标，播放倍率就会永远摆动。请改用本地单调锚点外推播放位置
  （`clock-controller`）；跨机器传递"过了多久"时，传的必须是**时长**，绝不是时刻。两个服务端时刻互相比较没问题
  （版本排序），两个本地时刻互相比较也没问题（流逝时间）。

- **快照的 age 在每次发送时现算，绝不存储。** `room:state` 携带 `playbackAgeMs`，好让中途加入的客户端知道
  手里这份快照已经陈旧了多久（服务端的 `withPlaybackAge`，接收端的 `resolvePlaybackAnchorAtMs`）。
  age 只在它被发出的那一刻为真，所以一旦存下来它就退化回时刻——这正是它挂在 `room:state` 载荷上、
  而不是挂在 `PlaybackState` 上的原因：后者是服务端持久化、客户端又回传的那个结构。
  每一处 `room:state` 发送点都必须打上它（共四处：bootstrap、`sync:request`、以及 `room-event-consumer` 里的两处），
  扩展端则在状态进入存储或被 member-delta 重新包装之前把它剥掉。

- **播放快照的到达时刻，必须记录在快照可被观测之前。** 一旦它写进 `roomSessionState.roomState`，
  正在重新水合的内容脚本（`content:get-room-state`）就能读到它，成员的加入/离开也能把它重新包装；
  而谁先做补偿，谁就会把它锚在**自己**的那一刻上，丢掉房间在此之前播过的一切。
  `markPlaybackArrival` 必须在写入之前、且在任何 `await` 之前执行。把 socket 消息串行化并不能覆盖这一点：
  那些读取方走的是 `chrome.runtime` 通道，不是 socket。

- **每个 `await` 之后，先确认手里的房间状态仍是当前的，再做补偿或投递。** 处理器是按 socket 消息逐条以
  `void handleServerMessage(...)` 启动的，彼此不串行，所以某个处理器在 await 期间（`ensureSharedVideoOpen`
  可能要开一个标签页）新状态可以后来居上。被取代的快照必须丢弃而不是投递：内容脚本的陈旧判断是按 actor 做的
  （`lastAppliedVersionByActor`），因此一份来自**另一位成员**的、已被超越的快照会被接受，并把播放拉回过去。
  `handleRoomStateMessage`、`applyRoomMemberState`、`expireBootstrapRoomStateWait` 各自都带着这道检查；
  新增的投递路径需要自己那一份。

- **凡是代表"这不是用户干的"的标记，都必须以它自己的窗口去问手势，且不得开任何例外。**
  `lastUserGestureAt` 是内容脚本判断某次导航/暂停是否出自用户的唯一证据，而 `userGestureGraceMs`（约 1.2s）
  是错误的询问跨度：任何窗口比它更宽的标记，都存在这样一段空隙——用户的手势已被遗忘，标记却仍读作新鲜。
  要问的问题是"这个手势有没有可能就是我眼下所见的成因？"，所以跨度必须取标记自己的窗口——
  既然它肯为一个倒计时等上 10s，就同样欠一次慢解析的 SPA 点击这份耐心。

  **该跨度锚定在标记自己的时刻上，而不是 `now`。** 让手势从 `now` 开始计龄、标记却从自己的时间戳计龄，
  会在尾部留下一条缝：标记仍然有效，手势却刚好过期。标记对 `[mark, mark + window]` 区间内的事件有效，
  而可能造成其中任一事件的手势落在 `[mark - window, now]`——所以跨度就是它，`now` 从判断中彻底消失。
  它的下界在另一个方向上同样吃重：没有下界的话，在一集 24 分钟的开头按下播放，会永久否决这一集的自动连播。

  **在该跨度内，每一个手势都推翻标记，没有例外**——尽管确实有些手势与标记并不矛盾：分享者把进度拖到最后几秒，
  其后真的会发生一次自动连播。#236 为了恰好放行这一个手势花了五轮复审，而每一次修复都在两种失败之间来回摇摆：
  放行手动选集点击（分享者把自己的私人选择推给了整个房间），或者误判一次真实的拖到片尾（房间悄无声息地不再推进）。
  信号无法区分二者——两者都是离散输入，一次点击可以落在 `seeking` 与 `seeked` 之间，
  而一次拖拽自身的松手 `click` 晚于开启它的 `pointerdown`。所以规则取那个笨办法，代价则写成一条测试记下来
  （"...the accepted cost of having no gesture exception"）：拖到片尾的分享者，手动分享下一集，仅此一次。
  重新引入例外，就是重新打开那场摇摆。

  整套方案之所以安全，是因为 `lastUserGestureAt` 只由**离散**输入刷新（`gesture-tracker.ts`：
  pointerdown/mousedown/click/touchstart/keydown/popstate），绝不由指针移动或滚动刷新——
  记录后两者的追踪器会把被动观看变成一票否决，从而悄悄废掉这个标记。

  **一次性标记必须被消费，而不只是被设期限。** 能推翻它的证据比它自己更短命
  （`resetUserGestureState` 在每次导航时把 `lastUserGestureAt` 清零），所以一个活过了它所解释的那次导航的标记，
  会在反对者已经消失的情况下再获得一次机会。请在处理器开头把它读进局部变量并清除。

- **被两种行为共用的窗口常量，其实是两个常量。** `INITIAL_ROOM_STATE_PAUSE_HOLD_MS` 曾同时是
  "页面加载自动播抑制多久"和"自然结束标记的有效期多长"（#236）。两者之间毫无关联，
  于是后者被悄悄钉死在一个为前者挑选的数值上——而 3s 短于 B 站约 5s 的下一集倒计时，
  这让标记在它本要捕捉的每一次自动连播之前就已过期。当一个常量被第二处调用点以不同的问题读取时，
  就把它拆开，并写明各自是以什么为度量。回归测试需要断言的那些数值放在
  `extension/src/content/timing-constants.ts`，而不是 `content/index.ts`：
  一条自己重新抄写数值的测试，在别人改掉线上那个数值之后，照样通过得心安理得。

## "地址栏是否标识在播视频"是路由自身的属性

在内容脚本眼里长得几乎一样的两类 B 站页面，对这个问题的答案正好相反。极性套反了不会得到
一个"降级的答案"，而会得到一个"自信的错答案"，#274 就是它的代价：页内切集之后，房间的共享
视频一直钉在上一集——却带着**新一集**的进度，于是其他成员反复被拉回上一集开头——直到分享者
刷新页面才恢复。

- `/festival/<id>` 在播放器走完整个播放列表的过程中，路由与打开时带的 `?bvid=` 都不会变。
  那里的地址栏是 {@link isAddressBarOpaqueVideoUrl} 意义上的"不透明"：page-bridge 快照是
  唯一的身份来源；而且一旦解析成功过一次，地址栏就被**证明**为陈旧，其解析结果不得再用作
  兜底（否则会答出"另一个非共享视频"，把页面强制暂停）。
- `/bangumi/play/ssNNN` 标识的是季，从不标识具体某一集，所以同理由快照优先。
- `/bangumi/play/epNNN` 标识的就是这一集本身。切到另一集必然改变它——页内切集走的是
  `pushState`——而且**地址栏先动**，`__INITIAL_STATE__`、`__playinfo__`、分集列表高亮项都在
  它之后才跟上。所以在这里，可能陈旧的恰恰是每一个页内来源，不可能陈旧的恰恰是地址栏。

于是在 `ep` 路由上规则整个反转。`video-identity.ts` 里的两个判据陈述这项比较，
`page-record-staleness.ts` 则把它一次性施加到页面给出的每一个来源上：

- **媒体事件同步触发，不等于视频身份可以同步判定。** 在 `ss` 路由上，`pause` / `ended`
  触发时，同步 `getSharedVideo()` 可能仍只能拿到季页兜底；复用缓存快照需要当时并不可靠的
  页面 DOM 来佐证（#291）。所以自然结束生命周期只在同步身份稳定时直接采用它；遇到不透明
  身份时，紧邻的 `pause`、`ended` 回调以及同一页面访问上并发的播放广播，共用一次新的
  `getCurrentPlaybackVideo()` 读取。这次读取必须在媒体事件回调让出执行权之前启动：B 站能在
  同一个 task 里先把地址栏推进到下一集 `ep`，若延后到 microtask 才开始，捕获的就会是目标
  页面访问。后一个 page-world 请求不能作废拥有本次交接的读取；即使 `ended` 到来时地址栏
  已经指向下一集，它也必须加入这笔在途读取，不能改信目标 `ep`。只有这次事件专用读取可以
  保留其起始不稳定页面访问所返回的快照；目标页面较新的读取不得取消它的交付，而这份保留的
  旧结果绝不能反过来覆盖新访问的共享缓存。普通“当前页面”读取仍须丢弃所有跨访问结果。页面
  世界的导航信号会先于快照回复抵达，因此导航控制器看到自然结束确认仍在途时，必须先加入它，
  不得推进已观察页面 baseline 或重置播放 generation；确认落定后再重试同一次导航、消费所得
  标记，然后才作废旧页面上下文。
  身份一旦确认，就随事件传入终集抑制定时器及其最终 paused 广播；定时器不得重新读取可变页面
  状态，也不得把已确认事件送入导航后的可变身份门控，让任一者抹掉已经证实的广播债务。自然
  结束标记和共享者抑制的武装时刻都锚在媒体事件自身，而不是后来的 bridge 回复；每个 await
  之后，都要重新核对播放上下文、播放器 session、video 元素与房间/共享归属，才能改变标记、
  保持、抑制或广播。后来的手势是重播/导航的**分类证据**，不是新的结构生命周期：因其变化丢弃终点结果
  会丢掉唯一的 paused 状态，而在 bridge 回复时才武装抑制又会把这项终点后证据伪装成旧手势。
  **绝不能把这条异步兜底扩到稳定的 `ep` 身份：** 那里页内全局仍可能指向上一集，而地址栏
  已经给出了权威的当前身份。
- **快照报出别的一集，含义是"还没解析出来"，不是"解析好了"。** 快照刷新调用方仍会
  得到 `null`，因此谁都不能把陈旧页内全局误当成当前集。但显式分享在 `ep` 路由上不再等待这份
  重复确认：`resolveCurrentSharePayload` 立即解析已经权威的地址栏。它的 8 次重试只留给
  `/festival/` 与 `/bangumi/play/ssNNN`——这些路由的地址栏不标识播放器里的具体视频，页面
  快照不可替代（#289）。
- **`ep` 路由绝不能被记为"地址栏身份已被否证"。** `rememberSnapshotResolved` 由
  `isAddressBarOpaqueVideoUrl` 把关，而后者只认 festival，正是为此。否证它等于把错答案钉死
  到这个页面生命周期结束为止——这恰好就是用户报的"只有刷新才恢复"。
- **"哪些来源是陈旧的"是一个问题，一次性对所有来源作答。**
  `markStalePageRecords` 接收页面给出的全部记录——高亮列表项、缓存快照、`h1`、文档标题——
  凡报出的集数不是地址栏那一集的即为种子，再沿"描述的是同一条记录"（共享 ep id、cid 或
  标题 key）向外传播。直接确认压过传播：报出的集数恰是地址栏那一集的记录，无论连到什么，
  永不被标记。

  这条规则的"逐个来源"版本，正是 #274 连着六轮复审卷土重来的原因。每一轮只否证被点到的
  那一个来源，而每一次否证都切断了承载证据的那条链，于是下一个来源把同一个错答案重新拼
  出来：高亮项在能与快照匹配**之前**就被清空，于是自身没有 ep id 的快照再也无法通过共享的
  cid 继承陈旧；接着 `h1` 复述快照的标题；`document.title` 又披着 `_番剧_bilibili` 复述
  一遍。一条记录有矛盾，三个来源轮流重建它。**要在一趟里追完整个等价类，否则这个类会以
  "一轮复审一个来源"的节奏自我重组。**

- **陈旧的来源要整个丢掉，绝不要在下游过滤它的输出。** 被标记的来源到达
  `resolveSharedVideoTitle` 时已经是空的——这也是该解析器重新变回朴素的"取第一个非空"的
  原因。事后过滤字符串，正是 `44 连影` 被拒之后 `document.title` 还能返回
  `44 连影_番剧_bilibili` 的原因：派生会把陈旧名从字符串比较底下洗过去。标题按
  `titleRecordKey` 连接，与解析器所用的规约是同一个，于是每次比较的两侧都过了它。
- **当所有标题都陈旧时，标签退化为集数 id。** 空白比朴素更差，但上一集的名字比两者都差，
  因为只有它是假的。
- **"采用一个身份"要的是确认，"作废一条记录"要的是证明。** 这是两道不同的门槛，代码里也
  相应有两个判据：`lacksAddressBarEpisodeConfirmation` 与 `contradictsAddressBarEpisode`。
  在 `ep` 路由上，快照必须被**确认**为地址栏所指的那一集才可采用——`bvid:cid` 快照根本不
  标识某一集（页内全局拿不到 `epId` 时页面桥就会给出这种结果），而在切集窗口里那正是上一集
  的 `bvid`/`cid`，从形态上与当前这一集的毫无分别。拒绝一个未获确认的身份不付任何代价，
  因为地址栏本身已经给出了完整答案。陈旧性则相反：它按证明传播，因为"链接"是关于记录的
  证据，不是猜测的许可证。两个判据在不标识某一集的路由上一律不生效。

让这个 bug 得以出厂的覆盖缺口值得当作警示抄下来：`share-controller.test.ts` 里所有 bangumi
用例走的都是 `ss` 季页，而在那里"快照优先"是对的，于是这条规则被跨极性套用却无人拦截。
其中一类路由的回归用例，对另一类什么都不能证明。

## 共享归属是推导出来的，而增量消息并不携带它

`sharedVideo.sharedByMemberId` 只在 `video:share` 时写入一次，它是一个指向易变身份（分享者的席位）的持久引用。
#235 就是它悬空之后的样子：没有人算得出 `isLocalSharedSource()`，于是没有人推进房间。
三条规则维系着它，没有一条由类型保证：

- **在构建时求解，绝不回写房间。** `roomStateFromSessions` 是 `sharedVideo` 抵达客户端的唯一出口，
  也是把存储的 id 与在线成员名单对账的唯一地方（`resolveSharedVideoOwnerId`）。
  新增的 `room:state` 构建点必须走它。持久化的房间刻意保留原始 id：那是**首选**归属者，
  所以一个只是网络抖了一下的分享者会在重连后夺回共享，而不是就此永久失去它。

- **完整的 `room:state` 只能在索引可证已清理干净的地方发布。** 换房时旧房间是在
  `createRoomForSession` / `joinRoomForSession` 内部离开的，而 `releasePreviousRoom` 会报告 `onRoomLeft`
  是否真的清掉了索引。`room_member_left` 增量消息无条件发出——它不读任何状态——
  但完整状态只在换房者回不来的地方发布：`publishPreviousRoomResync` 手握两张许可证之一即可，
  一是新的加入已经落座（它的写入会以**新**房间码重写整条会话记录），二是 `onRoomLeft` 本身已经落地。
  即使加入被拒，旧房间仍欠它一份状态，凭的是第二张许可证——因为回滚只撤销新房间那一侧。
  "会话哈希里已经写着新房间码"不是可以假定的事：那个哈希正是由 `onRoomLeft` 自己写的（#242）。

- **一条移动了归属的成员增量消息，欠房间一份完整的 `room:state`。**
  协议 >= 2 的客户端收到的是 `room:member-joined` / `room:member-left`，它们只编辑接收方的成员名单，
  别的什么都不改——接收方缓存的 `sharedVideo` 仍然指着上一份完整状态所指的那个人。
  `leaveRoom` 在 `needsRoomStateResync` 时额外发布一次 `room_state_updated`；加入路径同理：
  当新加入者在刚发给它的 bootstrap 状态里恰好是共享归属者时，也补发一次。
  这两处判断都不得替换成依据 `joinedAt` 排序的捷径：该值由处理这次加入的那个节点打戳，
  所以那是一次跨节点的钟比较，可能把成员顺序颠倒过来。任期规则的存在只是为了让归属不要每来一个人就重排，仅此而已。

- **一次离开在 `onRoomLeft` _成功_ 落定之前，不得发布任何 `room:state`。**
  该钩子把会话从房间索引里清掉，而 `getRoomStateByCode` 读的是索引、不是成员表——
  所以在写入仍排队时、或写入失败之后构建出的状态，会包含那位刚刚离开的成员，并把共享原封不动地还给他。
  `runRoomLeftHook` 是被 await 的，并会报告是否成功；app 层的实现会 await `runtimeStore.flush`。
  `room:member-left` 不受此限，失败时照发：它不读状态，所以脏索引污染不了它。

  除显式离开之外还有两条路径需要同样处理，而且都容易漏，因为在它们身上"离开"并不显眼：

  - 换房的成员是在 `createRoomForSession` / `joinRoomForSession` 内部离开旧房间的，
    而这两个函数自身什么都不发布——所以两个处理器分支都要自己释放旧房间。
  - 同样这两个调用，是在它们**可能失败之前**就离开了旧房间的（房间满、加入令牌错误、准入锁超时、房间码冲突）。
    `enterRoom` 在这条路径上也要释放旧房间，并以 `session.roomCode` 确有变化为守卫，
    否则一次根本没走到"离开"的失败会广播出一个成员从未离开过的房间。

## 运行时存储是写回式的，所以"排空"从不等于"写入成功"

`registerSession`、`markSessionJoinedRoom`、`markSessionLeftRoom`、`unregisterSession`
会同步更新本节点自己的表，并把共享写入排在其后。
下游凡是"写入、读回、然后据此做决定"的地方，都必须清楚自己问的是这两个问题中的哪一个（#242）：

- **`flush()` 说的是队列空了，`confirmWrites()` 说的才是写入落地了。**
  `flush` 等的是吞掉了错误的副本，所以一次失败的写入排空得与成功的写入一模一样。
  当重点在顺序时用 `flush`（"我自己的写入对我接下来要做的读是可见的"），当重点在持久性时用 `confirmWrites`。
  `confirmWrites` 是全存储范围的，并且会清掉它所报告的内容，所以答案的含义是"自你上次询问以来"；
  只需要确认**自己那一次**写入的调用方应当直接 await 那次写入，因为这四个函数都会如实报告各自的结果。

- **排队的写入会带退避重试，而一次重试可能活得比它的房间更久。**
  `durable-write-queue` 给每一次排队写入一份有界、带退避的重试预算。
  这重新打开了 #237 关掉的房间码回收风险：一次在房间码易主之后才落地的重试，会写进新房间。
  只有加入写入会把会话**加进**房间，所以只有它需要这道守卫——而且那枚 pin 是在 `markSessionJoinedRoom`
  **被调用时**读取的，绝不在可重试的函数体里读：函数体要等该会话的链条排空之后才运行，而排空是无界的，
  所以在那里取的 pin 可能已经指向这个房间码的**下一位**占用者，检查便直接放行。
  不匹配即 `NonRetryableWriteError`（代（generation）只会向前走，所以后续任何一次尝试都不可能绕回来）。
  代读不出来时宁可拒绝这次加入，也不留到以后再读，因为第二次读就是第二次钉错实例的机会。
  代**不存在**时仍然 pin 成 `""`，这正是拆除流程在那个键里留下**墓碑**而不是删除它的原因：
  删除会让"已拆除"与"从未打戳"变得无法区分，于是一枚 `""` 的 pin 就匹配上了它正要复活的那个房间。
  墓碑**不设过期**——TTL 必须活得比任何可能仍持有旧 pin 的写入都久，而这些写入没有上界，
  所以一个失效的墓碑会让 `""` 的 pin 再度匹配上一个不存在的键。回收墓碑的是下一位占用者的 `markRoomGeneration`。
  对墓碑**本身**取 pin 会被拒绝，否则一枚在拆除之后取的 pin 就会匹配上它。
  `hasRoomResidue` 忽略该键，所以墓碑绝不会让一个房间码一直被占着。
  任何按房间码落座或迁移数据的新写入都需要同一枚 pin；只碰以会话 id 命名的键的写入则不需要，因为会话 id 从不复用。

- **每一份重试预算，都要对着排空它的那个关闭步骤来配。**
  `close_shared_runtime_store` 与 `flush_pending_room_event_publishes` 各自带显式超时，
  超时会以 error 级别记录并报告为**降级（degraded）**步骤——于是一次仅仅因为等完重试而超时的关闭，
  会丢掉本来可以落地的写入（但**不会**让进程以非零码退出，见下面第三条 DEGRADED 规则）。
  `close()` 会先调 `stopRetrying()`，它会截断正在退避中的等待，**并且**丢弃尚未开始的写入，
  最多只留下**一次**在飞的尝试；步骤预算必须大于那一次尝试自身的超时。
  调高 `maxAttempts` 或任何一个延迟，都意味着要重做这套算术。

- **重试的节奏住在 `retry-pacer` 里，不在各个设施里。**
  退避排程、可被关闭打断的等待、不取消调用的单次尝试上限、以及对活过上限的调用的记录，
  是由 `durable-write-queue`、`pending-resync-queue`、`runtime-index-reaper` 和存储的命令包装器
  共用的**同一份**实现。它们曾是四份手写副本，而 #242 的复审意见里有六条是同一个缺陷出现在
  上一轮没碰到的那份副本上。新增的重试设施用这个 pacer，不要长出第五份副本。
  留在本地的是真正各不相同的部分：顺序/取代/确认、去重，以及由谁来决定重试。

- **跑光了预算的关闭步骤是 DEGRADED，不是 failed。**
  只有抛出异常的步骤才让进程以非零码退出（`graceful-shutdown.ts`）。
  这些预算之所以存在，正是因为这些步骤在等本进程无法取消的 I/O，所以"放弃等待"本就是设计中的结局。
  把超时当成失败，会把每一句"万一这个调用挂住了呢？"都升格成正确性主张——
  而这个问题没有最后一个答案，因为每加一道有界等待去回应它，那道等待自己又成了可以被同样发问的新调用点。
  #242 有十条复审意见都是这同一个问题的反复重提。两种结局仍然都以 error 级别记录；放弃排空这件事必须保持可见。

- **超时是答复调用方，它不取消命令。** 这一条在三个地方咬人，而修好其中一个不等于修好了它：
  - 会话的键，要等这次写入所启动的每一条命令真正结束之后才释放（`DurableWriteRequest.settle`）。
    在调用方被答复时就释放，会让补偿写入——它排在同一个键上——先跑，
    于是那条被放弃的命令落在它自己的回滚之上，留下一个客户端被告知并不存在、却能把共享赢回去的成员。
    `drain` 会等这些释放；`confirm` 刻意不等，因为一条仍在飞的命令早已给出过它的判定。
  - 没有任何地方会在第一次调用尚未答复时启动第二次——写入队列不会，`pending-resync-queue` 不会，
    reaper 的按房间发布也不会。否则一个挂住的依赖会按重试次数累积在飞命令。
  - 没有任何地方会在有在飞调用时关闭连接或总线：`close()` 先（有界地）排空链条再 `quit`，
    resync 的排空则先（有界地）等完那些被放弃的调用，之后关闭流程才关掉总线。

- **当同一会话有更新的写入排队时，重试就此放弃。** 越过这个点继续重试，是在和更新的写入较劲。
  这一点之所以成立，是因为加入写入重写的是**整条**会话记录，而不是只打补丁改 `roomCode`——
  于是一次丢失的 `registerSession` 会被下一次加入修好，而不是留下一个没有 `id` 的哈希，
  那种哈希会被 `loadSession` 读成"根本没有会话"。
  任何只携带记录严格子集的新增会话写入，都不得指望更早的那次写入已经落地。

- **索引写入失败的加入是中止，不是落座。** `runRoomJoinedHook` 会报告失败，
  处理器随即以 `leaveRoom(session, "disconnect")` 回滚这次加入——用 `"disconnect"`，
  是为了让重连的成员保住共享归属规则所依赖的那个身份。
  加入之后要发的一切都是从这次写入所维护的索引里读回来的，所以一个房间看不见的成员，
  比一次客户端会重试的加入失败更糟。而如果**回滚**也失败，就断开 socket：
  `leaveCurrentRoom` 在自身持久化失败且 socket 仍开着时会把成员恢复回来，
  所以在服务端仍占着席位的情况下告诉客户端加入被拒，会让两边就此各说各话。

- **剪掉孤儿房间索引项，仍然欠一次运行时拆除。** 定时对账与房间列表都会移除
  body 已不存在的索引成员，以保持枚举与计数一致；但只做移除，会把 room reaper
  原本能交给 `room-service` 的唯一房间码一并消费掉（#258）。因此每一条剪枝路径都
  必须原子地把带 token 的 claim 写进共享 `room-index-orphans` 哈希及其
  `room-index-orphans-queue` 投递索引。隔离不可读 body 时，删除其索引成员前同样要留下延后
  claim：坏 body 存在期间阻止投递，修复后清 claim，删除后才使其可投递。这里必须共享：
  独立的 global-admin 会做索引对账，却不运行
  room reaper。`deleteExpiredRooms` 只用 Redis 6.0 命令，以有界、轮转批次读取且不消费 claim，
  再次确认期间没有新 room body 占用该 code，并把仍是孤儿的 code 及 claim token 上报。
  `room-service` 只有在既有代守卫保护的运行时拆除确实完成后才确认该 token；
  每段脚本都必须在任何不可逆写入前验证两把交接键的类型，因为 Redis Lua 运行时错误不会
  回滚该脚本先前完成的写入。单点 room 读取与 sweep 都校验完整的持久化房间 shape（包括
  嵌套的 share/playback 状态）及 expected code：腐坏代表未知，不是 code 已复用的证据，
  也不能消费 claim。因此进程中途退出时，
  其他 room node 仍能接手，而同一 code 被回收再度成为孤儿后，迟到的旧确认也删不掉新的
  claim。

## 一次性广播需要重试轨迹，重复发送的则不需要

几乎每一条 `room_state_updated` 都会被下一次 `video:share` / `playback:update` / `profile:update` 重发，
所以丢一条只值一瞬。有两条是一次性的，一旦总线拒收，它们就永久丢掉这个房间（#242）：

- **共享归属 resync**（`publishSharedOwnerResync`）之所以触发，恰恰是因为房间已经停止推进，
  所以它后面什么都不会跟着来，而空闲的房间也不会发 `sync:request`——只有刷新页面才能恢复。
  它走 `pending-resync-queue`：该队列在一个立即返回的 `request` 背后带退避重试；
  `firePublishRoomEvent` 刻意不 await 它的包装器，而让离开/加入处理器阻塞在总线上会是更糟的取舍。
  一条记录会一直重试到总线收下为止——给单条记录设尝试上限，只是用更慢的方式丢弃一条没有别的东西会重发的通知——
  所以 `drain` 按设计是无界的，关闭时的调用则传 `{ final: true }`，它会先调 `stopRetrying`，
  最多留下一次在飞的尝试去等。一条记录在它的第一次发布尚未答复时绝不启动第二次：
  尝试上限是在和总线调用赛跑，并不能中止它，所以一个跑在挂住的总线之上的无界重试循环，
  否则会按重试次数堆起一条条在飞的 Redis 命令——和写入队列 `settle` 那条"超时不等于取消"是同一套推理。

- **运行时索引 reaper 的通告**，是唯一能告诉房间"某个死掉节点上的成员已经不在了"的东西。
  一旦本轮扫描清理完索引，`listClusterSessions` 就不再返回那些会话，
  于是之后的扫描再也没有任何线索能重新发现那个房间。
  reaper 自己保有一份记录集合，并在**每一轮扫描的开头**重试它——在"没有离线节点"的提前返回**之前**——
  只有发布成功才丢弃一条记录。这个队列和 `pending-resync-queue` 都不给积压设上限：
  驱逐或拒收一条尚未发布的记录，丢掉的正是它们存在的意义，所以积压只记录、绝不丢弃。
  正因为无界，每一条经过它的**关闭**路径都必须有界，而这样的路径有两条：
  `stop()` 以有界并发对着自己的截止时间排空，并且它在 await 在飞的那轮扫描**之前**就先置上 `stopping`，
  好让那轮扫描的串行排空及时让路，而不是先把整个积压跑完。只给第二条设界，预算照样会被打穿。
  超时的步骤会被大声记录下来，**并且**会让总线在有在飞发布时被关掉，而这些发布随后会像已经落地一样删掉自己的记录。
  每一次发布自身也有上限：一个只决定"要不要开始下一条记录"的截止时间，在总线是挂住而不是拒收时什么都界不住。
  扫描之间也不再重叠：它们共用那份集合，而 `stop()` 只 await 它知道的那一轮扫描。

  记录是怎么产生的，是这件事的另一半：一个房间只有在**那条**会话的清理写入被确认之后才会被通告，
  而会话记录正是重试得以可能的前提。扫描的各个步骤按它们所摧毁的东西排序——
  移除成员需要 `roomCode` 和 `memberId`，`markSessionLeftRoom` 会把 `roomCode` 抹掉，
  `unregisterSession` 会删掉整条记录——所以每一步都只在前一步被确认之后才运行，
  而没能落地的步骤（失败、被上限截断，或被 `stop` 打断）会把记录原样留给下一轮扫描从头再做一遍。
  每一步都是幂等的，这正是重做它不花钱的原因。#235 曾用相反的方式回答这个问题——它无条件通告，
  理由是 `unregisterSession` 反正会清掉同一个键，而设门槛"会让下一轮什么都没得重试"——
  这套理由只在扫描无条件执行 unregister 的前提下成立。
  `unregisterSession` 是唯一一处不被任何东西设门槛的写入，因为它返回 `void`
  （所以 `confirmWrites` 是唯一能看到它结果的地方），也因为它失败时房间索引本就已经干净，
  下一轮扫描重跑一次也不过是空操作。

## 不能超时的后台轮次，也就无法被观测

`room-reaper`、`room-index-reconciler` 与 `node-heartbeat` 每次触发都对 Redis 跑一轮异步任务。
这条链路上原本没有任何超时，两个 Redis 客户端也都没有——`lazyConnect` 与
`maxRetriesPerRequest: 1` 约束的是重试次数，而不是 Redis 已经收下的那条命令可以花多久回应。
于是连接半开时一轮任务会永久挂起，reaper 不再回收过期房间，却**没有任何**信号：
`bili_syncplay_room_reaper_sweeps_total` 的两条序列一起静止，只看失败率的告警不会触发，
恢复只能靠人工重启（#261）。心跳坏得一样、后果更重：`node_heartbeat_failed` 只能通过那一拍的
`.catch` 抵达，所以一拍永远不 settle 就什么都不会记，与此同时其他节点把它从集群索引里判老、
回收它的 session——而它还在服务客户端（#263）。
下面这些规则统一放在 `maintenance-pass.ts` 里——一份驱动，因为同一个缺陷在每一份手写副本里都出现了：

- **每一次触发都恰好记下一个结果。** 只有这样，"速率变平"才只能意味着"定时器没了"。
  超过上限的一轮记为 `error`，而不是沉默。如果上限只报告**第一次**僵死的触发，
  僵死持续期间序列又会重新安静下来——那不过是把原来的 bug 多绕几步。
  但"记下来"不等于"算失败"：发现上一轮还在上限**之内**跑着的那次触发，有自己的
  `skipped` 标签——间隔是个只要求为正整数的配置项，完全可以被设得比上限还短，
  把它记进 `error` 会让一个正在正常回应的依赖把失败率顶到 1（#262 复审）。
  于是 `stalled` 必定跟在同一条调用的 `timed_out` 之后——runbook 就是这么教运维读它的。
- **上限不取消调用，所以一轮绝不叠在另一轮上面。** 没有任何东西能中止已经发出的 Redis 命令，
  上限只是让调用方不再等待。上一条命令尚未回应就再次触发，会按每个周期一条的速度堆积命令；
  而且——因为关服步骤等的是**最后**一次触发存下的 promise——会让关服在等最新那一轮，
  更早的几轮却还在写。同样的推导见 `pending-resync-queue` 与 runtime index reaper 的逐条发布上限。
  占位是由调用自身的回应释放的，不是由上限释放：晚一跳释放会把下一轮判成 `still_running`，
  直接把扫描速率砍半。
- **`stop` 要等真正的调用，但要有界——预算不够时还要说出来。** 下一个关服步骤会关掉 Redis 连接，
  所以命令还在空中就返回等于和 `redis.quit()` 赛跑；但无界等待只是把超支挪进关服步骤，
  然后那一步被记成失败。`retry-pacer` 的 `settleTracked` 就是这个有界等待，
  其预算必须留在该步骤自身的超时之内。而"悄悄放弃"是同一笔交易的反面：
  这场赛跑原本**正是因为**那一步超时才被看见，所以干净返回的 `stop`
  欠调用方一条 `onSettleTimeout`，把仍未回应的调用数报出来。
  在同一次改动里既给等待加了界、又把它的信号丢掉，正是"治沉默的修复在下一步重新制造沉默"的做法。

- **上限是由"这一轮迟到要付什么代价"推出来的，不是拍脑袋图省事定的。**
  reaper 是固定 30s（默认间隔 60s）。心跳则是算出来的（`heartbeatTimeoutMs`）：半个间隔，
  且不超过 `NODE_HEARTBEAT_TTL_MS` 的三分之一——因为一拍迟到的代价是别的节点在 `staleAt`
  把它判老、在 `expiresAt` 回收它的 session。上限如果跟过期同时触发，那就是在回答一个
  已经没人能据此行动的问题。"低于间隔"是这条规则的另一半：正是它让超时之后的那次触发
  是 `stalled` 而不是 `overlapped`。

上限属于调用方，不属于连接。#271 已经把另一半定了下来——见
[约束一条 Redis 命令的是两层，不是一层](#约束一条-redis-命令的是两层不是一层)——它落
下的分工没有动摇这条规则：房间存储与 runtime store 都刻意不带 `commandTimeout`。一道几
秒之后才生效的兜底，回答的是当时还持有命令的那个人；它无法回答一次已经放弃的触发，也
无法告诉下一次触发上一次是否还悬着。尤其 `heartbeatNode` 是直连的 `MULTI`——它不走写
回队列，所以队列自己的 `pendingOperationTimeoutMs` 从来就没管到它。给任一连接加兜底都
会连带结算它的请求路径（`get_room` / `update_room`），那是另一个需要单独权衡重试语义的
决定——#261 有意没有做。

## 无界的写入队列会把"僵死的依赖"变成"还在增长的依赖"

`redis-event-store` 把每次 append 串在一条 promise 链上，让 stream 的顺序与事件顺序
一致。但这条链上没有任何一环有上限，而喂它的是**每一条**结构化日志——于是第一条永不
返回的 XADD 之后，后面每条日志都变成又一个闭包，各自捕获着自己的事件正文，既没有上
限也没有去重。只要 Redis 一直僵死，内存就随日志速率增长；`queryEvents` 等在同一条链
上，后台概览的每个计数也是；`close()` 是 `await pendingAppend`，因而必然超出
`close_event_store` 的预算（#264）。规则如下：

- **不能拒绝工作的队列，不受任何东西约束。** 单次写入的上限与队列深度上限回答的是两
  种不同的故障，互相不能替代：上限在 Redis 不再回应时触发，深度上限在 Redis 回应得
  比事件产生得慢时触发——后一种状态下任何上限都不会触发，而队列会一直长下去。两者
  缺一不可。
- **在这里丢弃是对的取舍，在别处不是。** 事件流是可观测数据，它自己还带着 `MAXLEN`；
  丢条目的代价是列表不完整，而丢弃计数会把这件事明说出来。这与 `pending-resync-queue`
  正好相反——那里丢了就是永远丢了，见
  [一次性广播需要重试轨迹](#一次性广播需要重试轨迹重复发送的则不需要)。
- **把故障报成事实，不要报成"一次事故"。** 第一版把它报成有起点、有终点、有总量、
  原因还会升级、且有两种终结方式的一段"事故"。随后 #266 用四轮复审找出了配对断掉的
  各种状态：节点流量安静下来、关服抢先到达、写入以拒绝告终、阶段变化多打了一个起点、
  终点被调高的 `LOG_LEVEL` 滤掉。这不是运气差。起止配对就是一个 span，span 带着不变量，
  而日志流里没有任何东西能保证不变量——尤其是在"依赖正在坏掉"的那个组件里，于是那个
  依赖的每一种失败形态,都是配对断掉的又一种方式。`maintenance-pass` 能用同一个形状，
  只是因为定时器保证了每一拍离散且必然结束；**模式的保证来自它的前置条件，不来自它的
  形状**，而 append 路径是调用方驱动的连续流，两者都继承不到。取而代之的是：按原因限流
  的一行"正在发生什么"，外加一个计数器——而"还在不在发生"和"发生了多少"，计数器从第一版
  起就无状态地答对了，一条意见都没挨过。
- **上报不得依赖它所上报的那个东西。** 这些行经 `logEvent` → `eventStore.append`，
  于是上报与它正在上报的容量互相争抢，生出自反回环、日志级别路由问题，以及容量边缘
  每完成一次写入就抖一次。一个错误的依赖方向，贡献了四条意见。`logger.ts` 把"排除出
  store"与"固定 error 级"放在一起，因为它们是同一个原因。
- **被丢弃的 append 仍然成功地答复调用方。** 调用方是结构化日志器，它会把一次拒绝变成
  一行 `runtime_event_append_failed` 写到 stdout。日志器把这些行按诊断限流为每分钟至多
  一条，覆盖 Redis 快速拒绝以及所有 event store 实现。限流器最多单独跟踪 32 种活跃诊断，
  超出的诊断共享一个 overflow 桶，避免攻击者可控的错误文本反过来让限流器自身的内存或
  输出无界；但丢弃路径仍不该让每个调用方各自处理同一个依赖故障。改为聚合上报：每次丢弃
  都进计数器，另有一行按原因限流（每原因每分钟至多一条）的丢弃日志（#268）。
- **上限不会放行这条链。** 它只是把存储切到丢弃模式；这一环本身仍然等待真正的答复。
  放行会让第二条写入落到一个两次都没回应过的连接上，并且在 Redis 恢复时乱序落库——而
  顺序正是这条链存在的理由。
- **读取不该排在它想读的那批写入后面；过了某个点更不该发出。** 这条链是串行的，所以
  `await pendingAppend` 会让一次读取依次等完每一条排队写入的**发出**与应答——那些往返
  甚至还没开始。给这段等待加界之后，读取只排在唯一那条在途写入后面。但只要那条写入
  不回应，读取同样回不来，而"等久一点"根本就是拿错了杠杆：后台事件页与
  概览页都每 15s 自动刷新，于是只要僵死还在，每一次轮询就往 ioredis 队列里再留下一条
  读和一个闭包——正是本节要消灭的那种、由定时器驱动的增长（#266 复审）。所以读取是被
  **拒绝**（`503 event_store_unavailable`），不是被延后。无界队列的解法，从来不是给
  "等它多久"加一道界。
- **"队列排空了没有"不是读取要回答的那个问题。** 第一版有界实现等完这条链之后，不管
  等到的是什么都照样发出读取，只有在 append 上限触发后才拒绝——而那是 5 秒之后，因为
  这个上限本就故意设得长（触发一次要丢记录）。这中间的每一次读取都排到了一条永远不会
  回来的命令后面，于是这道界本要消灭的缺陷原封不动地活了下来（#269 复审）。而且，一个
  仅仅是落后的 Redis，队列同样排不空，按这个答案去拒绝会在 Redis 正常工作时把控制台
  弄下线。真正的问题是连接**在不在回应**，能回答它的只有队首那条命令——而且是在**读取
  自己**的预算内，不是上限的预算内。两种行为，两个常量，又一次。
- **一条超时的读取，和一条超过上限的写入，是同一种证据，必须同样被记住。** 这道界的
  第一版答复了调用方却忘掉了那条命令。在 append 安静——或者正在被丢弃——的节点上，
  队首检查根本没有在途命令可看，于是下一次轮询畅通无阻地又排进一条读取，本节要消灭的
  "每轮一次"的增长在读取这一侧原样重现（#269 复审）。超时不是一条命令的终点，而是
  "已经知道这条连接坏了"的起点。用计数而不是布尔，因为写入链是串行的、读取却可以同时
  有好几条在途；而且命令最终应答时要释放，否则一次短暂的慢就会把后台页面按住直到进程
  重启。
- **那道检查是关于过去的证据，所以读取还需要它自己的一道界。** 读取排在它被**发出**的
  那一刻连接上的东西后面，而"检查之后、命令之前"才开始的僵死，任何发出前的检查都看
  不见。在那里再验一次队首既补不上这个缝，又会毁掉这条路径要保护的场景——有队列的节点
  上，队首几乎总是几毫秒前发出、尚未应答的写入，要求队首已应答等于在一个仅仅是落后的
  Redis 上拒绝每一次读取。于是两道界分工，且互不替代：队首检查挡住"僵死期间每轮轮询都
  发一次读取"，读取自身的命令超时挡住"僵死开始时已在途的那一次读取"一直等到 Node 默认
  它根本不会被答复——Node 的 `requestTimeout` 约束的是**接收**请求，不是产出响应，所以它
  并不是 #269 当时以为的那道兜底（#277 实测）。代价是僵死起点漏出**一次**被拒绝的读取——下一
  次轮询会发现连接没有应答，发出任何命令之前就会被拒绝。
- **`close` 先有界排空，然后直接断开 socket——`QUIT` 不是逃生口。** 直接丢掉队列会在
  每次正常重启时丢掉关服自身的事件；无界等待则会在每次僵死关服时把这一步判为失败。
  event store 是日志器的汇，所以它的关服步骤排在所有共享生产者之后；提前关闭会静默丢掉
  它们的收尾事件。`close` 开始后仍到达的 append 会计入 abandonment 报告的
  `closingAppends`。关服步骤超时只答复调用方，并不会取消真实生产者；所以如果 append 在
  event store 步骤返回后才到达，会再发一条累计更新，而不是越过一次性的最终回调后无声
  消失。然后：在预算内等这条链，超出预算后让还没开始的环停下——连接即将消失，此后发出
  的命令会被拒绝，而日志器会在关服后生成受限流的
  `runtime_event_append_failed`。然后是 `disconnect()` 而**不是** `quit()`：ioredis 把
  `QUIT` 和其他命令放进同一个 `commandQueue`，应答从队首依次配对，所以优雅关闭会原样
  继承刚刚被限住的那段等待（#264 复审）。链排空时仍走优雅路径，但同样有界——半开的
  socket 会在没有写入可归咎时吞掉 `QUIT` 的应答；而这道界与这里的其他每一道一样欠一行
  上报（#266 复审）：它刚刚花掉了整个预算，而一个干净返回的 `close` 是它与"被记成成功
  关服"之间唯一的东西。`settleWithin` 回答的是"落定了没有"——这对排空是对的（被拒绝的
  写入也是一个答复），对 `QUIT` 是错的（一次拒绝落定得很干净，却把 socket 留在没人检查
  过的状态），所以那里是三种结局而不是两种。只做有界而不上报，与
  [后台轮次](#不能超时的后台轮次也就无法被观测)那条是同一个反向取舍，因此有
  `runtime_event_appends_abandoned_at_shutdown`。

一条连接，应答按顺序。这既是"只有 `disconnect` 才是有界关闭"的原因，也是那道读取拒绝
的推导来源。它同样是那道拒绝的边界：存储只能依据**自己**某条命令给出的证据去拒绝，
所以进入僵死后的**第一个**请求——无论它是读是写——都不会被拒绝。它会被有界地判为不可用
并答复调用方，然后它自己成为拒绝下一个请求的证据。这已是调用方一侧的界能做到的极限；
要彻底补上，需要独立的读连接。

`commandTimeout` **不是**另一条出路，#271 已就两个 append 链存储把这一点定案。它会与
每次写的上限抢跑，从底下把命令 reject 掉并清掉 `writeIsStalled`——而那正是这道拒绝赖以
成立的证据——于是一条"冻住并廉价丢弃"的链，变成"每个超时磨一条命令"，同时让每一次轮询
重新回到一条已死的连接上。兜底是活性界，它无法替代一道**产出证据**的界。这个存储的测试
夹具只有模拟了这种顺序才值得信：让每次调用各自独立完成的夹具，会乐于"证明"读取和关服
能绕过一条僵死的写入。

## "哪条记录可以丢"是记录的属性，不是队列的属性

`redis-audit-store` 有一条和 event store 逐个环节一模一样的链，后果也一模一样
（#267）。它唯一不能照搬的是答案：审计记录是全系统唯一说得清"房间是谁关的、成员是谁
踢的"的东西，静默丢弃不是任何人可以替运维做的取舍。由此得到的规则：

- **抽出机制，把策略留在调用点。** 四道边界现在是 `admin/append-chain.ts`，两个存储
  的差别只在 `onRefused` / `onAbandonedAtShutdown` 两个回调里——事件存储返回它自己
  构造的记录，审计存储抛出。手写第二份链，正是 #242 里造成 6 条重复意见的那个形状，
  其中一半是"修了 A、漏了同构的 B"。
- **让"丢弃"划算的是喂养速率，而这不是设计里的常量。** 事件存储不能拒绝，因为它的
  调用方是结构化日志器，一次拒绝就是一条日志一行 stdout 错误。审计链由管理动作按人的
  速度喂养，所以"一次拒绝一行日志"付得起——而且这行日志是
  `admin_audit_log_append_failed`，`action-service.writeAudit` 早在这一切之前就已经
  接住它了。
- **已有序列能回答的问题，不要再加一个计数器。** 事件存储需要
  `bili_syncplay_event_store_appends_dropped_total`，是因为它的丢弃本来无声。审计的
  拒绝并非如此：`metricsCollector.recordEvent` 在每次 `logEvent` 时都会执行，不受
  `LOG_LEVEL` 与采样影响，所以
  `bili_syncplay_events_total{event="admin_audit_log_append_failed"}` 已经无须任何
  新增面就回答了"还在不在发生"和"发生了多少"。
- **管理动作照样成功，正因如此这次丢失必须够响。** 审计写入一直是发后不理的；在
  Redis 故障期间把管理能力一并下线是更坏的失败。既然动作无论如何都会发生，那么"丢了
  一条问责记录"和"没人知道"之间，就只剩下"拒绝是否可见"这一道。
- **关服步骤的预算属于步骤，不属于步骤里的某个组件。** `close_admin_services` 关的是
  管理会话存储**和**审计存储，而会话存储那句 `await redis.quit()` 原本也是无界的——
  只修审计存储的话，同一个 Redis 照样会让这一步失败。两个关闭现在一起 settle，而不是
  顺序 await，所以其中一个抛出不会跳过另一个的关闭。现在所有有界的 Redis 关闭都共用
  `quitWithin`；策略与预算仍留在各自调用点。

另外四个 Redis 设施也遵守同一规则（#270）：

- `redis-room-store`、`redis-admin-command-bus`、`redis-room-event-bus` 各自独占默认
  5s 关服步骤。它们给 `QUIT` 4s，给关服调度与降级上报留下 1s。两个总线通过
  `quitAllWithin` 并发关闭 publisher 与 subscriber；其中的 `allSettled` 保证一端关闭
  出错不会藏掉另一端 socket 的结果。
- `redis-runtime-store` 独占 15s 的特殊步骤。最坏情况是：收束后的队列用 5s 等在途尝试
  和刻意不设超时的在线调用方，再用 5s 等所有越过调用方等待的 Redis 命令真正结束，
  最后用 4s 等 `QUIT`；合计 14s，同样留下 1s 余量。每条命令都在运行时存储的 Redis
  客户端边界登记（包括直接读取与 `MULTI.exec()`），所以调用方已超时或上游关服步骤已
  放弃等待，都不会让命令从关服上报中消失。
- 非 `ok` 结果会断开 socket，并发出对应设施的 `*_close_unfinished` 事件。总线的上报
  还带客户端角色；运行时存储只要仍有调用方、命令、或节拍器手里的 attempt，即使
  `QUIT` 自己成功也会上报，并带上**三**类数量与调用方 drain 预算。是三个，因为排空
  等的是两个互相盲区的判据：命令集会重查，抓得到排空期间新发的命令，但在同一个
  attempt 的两条命令之间读作空；节拍器那一份跨得过这些缝，却只快照一次。只等——或者
  只报——前者，就会出现 `pendingCommands: 0` 而全程沉默的关闭（#272 复审）。只有边界
  却没有这些行，只会把原先 `server_shutdown_step_failed` 的沉默下移一层。
- 总线的终态关闭不再追加第二条 `UNSUBSCRIBE`。consumer 的普通退订可能正是半开 socket
  已经不回答的命令；`QUIT` 本来也会退出订阅模式，直接进入它的边界才能保证强制断开
  兜底可达。关服以外的逐命令边界属于下面这条连接级策略。

## 约束一条 Redis 命令的是两层，不是一层

#261、#263、#264、#267、#270 是同一个缺陷——Redis 接收命令却不再应答，于是某个调用方
无界地等下去——被五个不同症状分别找到。每一个都在"症状消失"时收尾，所以同一个被推迟的
问题回来了五次。#271 给出了答案，而这个答案是一条**区分**，不是一个数字。

- **deadline（期限）** 是按行为定的，从"这个调用方能承诺什么"倒推，并且**决定接下来
  做什么**：丢弃、拒绝、重试、中止。`append-chain` 每次写的上限、它的读取界、
  `pendingOperationTimeoutMs`、管理命令总线的应答计时器——数值各不相同，因为问题各不
  相同。
- **`commandTimeout` 是活性兜底。** 它只回答一个问题——这条连接是不是不再应答了——
  所以对所有采用它的连接是同一个量级（`REDIS_COMMAND_TIMEOUT_MS`，5s），从 Redis 的
  时延分布倒推，而不是从任何调用方的耐心倒推。它从不决定接下来做什么，只保证有人做。

一条连接至少要有其中一层，而七条里有四条两层都没有。但这两层**并不能叠加**，而这才是
决定"哪条连接取哪一层"的东西：

- **兜底无法替代一道"产出证据"的界。** 本仓几乎每一道期限都建立在同一套机制上——上限不
  取消调用，所以调用仍被追踪，而**它持续的沉默就是阻止下一次尝试的东西**：
  `ensurePendingCapacity` 统计 `commandPacer.trackedCount()`（#242）、`maintenance-pass`
  报 `stalled`（#261、#263）、`pending-resync-queue` 等 `inFlight`（#242）、
  `append-chain` 依 `writeIsStalled` 拒绝读取（#266、#269）。兜底会把这些调用结算掉，
  于是每一道界都把连接读成空闲并放行下一次尝试：它不再是界，而变成"每个超时窗口多一条
  命令"的速率。这个选项会一次性废掉上面四条。
- **所以判据不是"它是不是已经有界了"。** 只有当这条连接上**没有任何调用方从"命令没有
  应答"里推导出一道界**时，它才可以设兜底。三条通过：管理会话存储，以及管理命令总线的
  两个客户端。五条不通过。
- **声明是强制的，而且必须点名那道期限。** 所有客户端由 `createBoundedRedisClient`
  构造，它的 `RedisCommandBound` 要么是兜底，要么是一条被点名的调用方一侧期限。"这条
  已经有界了"这句话在运行时存储上被相信了很久，只因为没人必须写下界在哪——而
  `trackAwaitedOperation` 上一道界都没有。`redis-client-bounds.test.ts` 保证
  `new Redis` 不出现在别的模块里，因为这个选项的缺席在 diff 里看不出来，它正是这样连着
  五次没被看见的。
- **豁免不等于没问题，而修法是一道"保持调用被追踪"的上限。** 房间存储和运行时存储的请求
  路径原本一道调用方界都没有，僵死的 Redis 在那里挂住一次 WebSocket join，全程没有任何
  东西在倒计时。#277 用两个 store 上的 `boundCommand` 收尾：`capAttempt` 答复调用方、
  把命令继续留在追踪里，于是 `ensurePendingCapacity` 与 `maintenance-pass` 读到的仍是
  连接级选项会摧毁的那份证据。界的声明一行没动，这正是要点——两层依旧是分开的。
- **该用哪道界是**调用**的性质，不是方法的性质。** 两类调用方共用这两条连接、并且会走进
  同一批辅助函数：`loadSession` 既在 join 路径上、也在运行时索引 reaper 里，
  `readRoomBody` 既在管理端列表里、也在索引对账里。所以界是传进去的（`CommandBound`），
  后台通道传 `boundedByOuterCaller`——这是一句写下来的断言：更外层有人会停止等待。给它们
  加上限会让 `stalled` 变得不可达、让下一 tick 压在上一趟没回来的 pass 上跑，那就是换条
  路走回 #261 和 #263。`redis-store-command-bounds.test.ts` 两个极性都断言，并对每个
  请求路径方法逐条挂起第 k 条命令，因为"第一条有界、第三条没有"的方法能通过任何单点探针。
- **界属于每一条命令，绝不属于整段操作。** `getRoom` 每个成员读一次会话、
  `purgeSessionsByInstance` 每个残留会话读一次，按方法设总预算会让健康的 Redis
  因为"有数据"而失败——和给启动迁移设一个总预算是同一个错（#271 复审）。
- **一个只是"搭上"后台 pass 的请求，要设界的是它的等待、不是那趟 pass——而且界要设在
  "沉默"上，不是设在"时长"上。** 房间列表要等第一趟索引对账，而对账自己的命令是刻意不设
  上限的；`awaitBootstrapReconcile` 转而给这次**等待**设界，于是 pass 照跑、下一个调用方
  仍能搭上它。若在这里设总预算，大库上一次**健康**的迁移期间所有管理端列表都会失败——这和
  给整段启动迁移设一个总预算是同一个缺陷。所以它只在"整整一个窗口内没有任何一条对账命令
  得到应答"时才放弃，这也是为什么每条 pass 命令都要声明 `boundedByOuterCaller` 而不是
  直接调客户端。那次被吸收的 rejection 同样不是可选项：pass 比这次等待活得久，而 Node 22
  上一个无人处理的 rejection 会直接结束进程。
- **一道可能被撞上的上限，绝不能被正常扇出撞上。** 准入是"拒绝式"的安全边界，不是调度器。
  凡是对"规模由部署决定"的集合做映射的读——房间列表的 `REPAIR_CHUNK_SIZE` 批、每个会话或节点一次
  `HGETALL`、管理端对每个房间发问——都会直接撞上它，并在**完全健康**的 Redis 上失败（257 个
  房间就够了）。这些扇出各自走一个容量低于准入上限的等待式 `concurrency-limiter`；而且限流器
  放在**扇出处**，不放进 `boundCommand`：给每条命令前面加限流器，会在僵死时自己长出一条无界
  的等待队列，那正是它要防的缺陷。`ADMIN_ROOM_FANOUT_LIMIT` 按**服务**分配而不是按调用，
  因为并发调用会把"按调用的批"乘起来。运行时存储的节点与会话读取共用同一个限流器，理由相同：
  两个各占准入上限一半的独立池子合起来，仍能把整份准入预算吃光。
- **一道界绝不能以同步抛出的方式离开它所在的函数。** 有两个调用方用两条受界命令拼
  `Promise.all([...])` 字面量。第二条同步抛出会让整个参数列表被丢弃，而第一条命令已经发出、
  且再没有人接它；它的上限随后触发成一个无人处理的 rejection——Node 22 上这会直接结束进程。
  两个 store 的 `boundCommand` 都是 `async`，仅为此。
- **Node 的 `requestTimeout` 不是慢 handler 的兜底。** 它约束的是**接收**请求，不是产出响应，
  所以一个在等僵死 Redis 的 HTTP handler 永远不会被答复——这是实测结论，而 #269 和 #277 的
  第一轮都曾在注释里倚靠它。任何"这条路径至少还有 HTTP 服务器兜底"的论证在这里都不成立。
- **两条连接上都不再有无界的写。** `updateRoom` 是最后一个，而它**不是**靠重新论证 #237 离开的
  ——它的 CAS 一直都是「以整份前体正文为条件」的。它离开，是因为每一个「成功后欠着别人不会重复
  的后续」的调用方都已经把这件事说出来了：孤儿回滚与离房的过期排期**具名**自己的期限（并且走准入
  不设上限，因为带上限的读会在第一次超时时结束整条效果），加入**上报**它没能确认的那次复活，
  管理端清空视频也**具名**自己的期限——它的成功欠着**两样**别人不会重复的东西：审计记录**和**
  `room_state_updated` 广播，所以那个写会活过这次等待，两份后续都归效果所有；未确认的清空按
  未确认审计，而不是声称已完成。它同样走**删房用的那一道关服闸门**，而不是把那个形状手抄一遍：
  **每一个会启动房间效果的动作都该待在同一道闸门后面**——在关服快照之后才被受理的效果，没有人
  等它、也没有人排空它；而「手抄一个效果的形状」正是这里连续两次漏掉部件的原因。剩下的那些可以安全丢弃结果，
  因为下一次分享、播放或改名的写会覆盖它。

  **「有条件」保证的是迟到落地本身安全，它从来不抵掉这个写成功后欠下的东西**——而抵掉它的办法，
  最后并不是「把上限挪到别处」，而是让每个调用方各自说清自己的成功欠着什么：两个具名期限、
  两个上报、三个自然覆盖。

  `revokeMemberToken` 是最后一个离开的，方式与其他几个相同——靠**守卫变成必填**。它的脚本只在
  「提出撤销的那个 session 仍然拥有这个 memberId」时才结束该身份，所以一次在上限之后才落地的
  撤销，够不到继任者正在使用的绑定，而那正是 #237 当初的顾虑。让守卫得以变成必填的，不是一段
  论证，而是 #277 更早的一块交付：踢人——唯一一个意思是「不管现在是谁持有」的调用方——早已改走
  `evictMemberToken`，于是不带 session 的那条路径连一个生产调用方都不剩了，与在它之前的
  `blockMemberToken` 一样。**一个写之所以变得可以设界，可能是因为「另一处改动」拿掉了那个让它
  无法设界的调用方**；重读一个写上写着的理由，和重新推导它一样值钱。

  给它设界还挪动了**离房在哪一步撤销**，而这次重排才是这项改动的实质。`room:leave` 原本先移除
  成员、再撤销。一个有上限的写可以在尚未被应答时就答复调用方，所以在那个顺序下，每一次被上限
  答复的撤销都会留下一个「已经被从运行时里抠掉、必须有人放回去」的成员——而那个放回去的写会把
  一个可能已经换手的身份重新入座，正是撤销自己的守卫要防的那种覆盖。四轮复审都花在给这个补偿
  加守卫、排顺序、处理迟到结果上，却没人先问那个更简单的问题：**为什么会有东西需要补偿？**
  把撤销放到最前面就回答了它——撤销失败或未确认时，成员原封不动地留在那里，离房失败，没有任何
  东西需要撤销。它同时也把守卫当初所针对的那个**活着的绑定**还给了守卫：`removeMember` 会删掉
  该绑定，所以跑在它之后的撤销比对的是「什么都没有」。**一个补偿如果需要自己的守卫、自己的
  顺序、自己的迟到结果处理，那是在提示：被它补偿的那步操作放错了位置。**

  它同时也把「一个带上限的写，它的**本地镜像**更新可以挂在哪里」这件事磨清楚了。撤销把镜像更新
  挂在**被上限的**那个 promise 上，而不是被追踪的那个：调用方据以行动的是被上限的那个答复，而
  一次迟到的镜像更新会删掉 `requireMemberToken` 用来校验每一条消息的那个 token——此时这次离房
  早已报告失败、成员仍在座位上。姊妹方法 `evictMemberToken` 把镜像留在被追踪的 promise 上，而且
  这是对的：没有人会去撤销一次踢人，所以它迟到的应用正是期望的终态。**要问的不是「这个写有没有
  上限」，而是「有没有人在被告知失败时把它撤销掉」。** 一个有上限的持久写还欠自己一份终态上报，
  因为在上限之后才到达的失败，通过返回的 promise 到不了任何人手里——而这两半不能重叠：
  `boundDurableWrite` 无论哪一侧先答，**计数只加一次**，但两条**日志**都保留，因为只有迟到的
  那条带着 Redis 到底说了什么。两边都计会把告警读到的故障率翻倍；去掉终态上报则会把「立即失败」
  整个丢掉，因为一个有上限的**读**，它的 rejection 没有任何人计量。`trackOperation` 当初也需要
  同一个标志位，这是它的第二份，所以要放在一处（#266、#277 复审）。独立的 `blockMemberToken` 路径和房间存储中无条件写入的
  `saveRoom` 都没有生产调用方，所以 #277 直接删除了它们。**一个写离开这张表靠的是变成
  「有条件的」，而不是重新论证 #237**：有守卫的写迟到落地是 no-op，所以它给调用方的那个
  答复不可能是错的。`markRoomGeneration` 是第三个这样离开的，而且它拿的是普通的请求路径
  上限而不是调用方一侧的期限——建房是它唯一的调用方，没有人从它的沉默里推导任何界。它的
  pin 属于**请求**：由建房方读出该键的值再传进来。把这次读放进 store 内部会重新打开守卫刚
  堵上的洞——一次在调用方放弃之后才答复的读，pin 到的是**后继者**的值，守卫于是原样放行这
  次过期的写。被拒绝的写不是 Redis 的故障，所以建房方回滚这间还没有成员的房间，并报告
  `reason=room_generation_superseded` 而不是存储错误。这次回滚正是让「没盖上 generation 的
  房间」不至于变成永久孤儿的东西——没有成员且没有 `expiresAt` 恰恰是 reaper 永远不收的那
  种——所以回滚写不进去时现在会打一行 `room_rollback_failed` 而不再被吞掉：给写设上限之后，
  这条路径不再只有 Redis 报错才能走到，超时和输掉代号同样会走到。回滚遇到版本冲突**不等于**
  「没有东西要收」——它只说明这条记录动过，而管理员碰了我们这间还没有成员的房间同样会让它
  动过——所以回滚会重读、用 joinToken 比对这条记录是否仍是我们那间，并在自己的尝试次数上限
  内重做 CAS；只有真正没能过期掉的房间才会被上报。

  **「有条件」保证的是「迟到落地这件事本身是安全的」，它并不抵掉这个写在成功之后欠下的后续
  动作**——而后半句才决定上限能放在哪一层。所有已经拿到上限的写都具备同一个形状：**一个**
  调用方拥有**一份**后续。两个有守卫的删房保住了回收计数、运行时拆除和 `room_deleted` 广播；
  `markRoomGeneration` 的建房方负责回滚自己那间房。

  这六处里有一处是靠别的路离开的：**一件簿记失败了，不构成撤销它所属的那次操作的理由。**
  `room:leave` 给腾空的房间排期过期，而此时成员早已移除、会话早已清空。在这个写上抛出，会把
  离房送进 `restoreLeaveState`，把一个成功离开的成员重新入座——并让房间正文说着「正在过期」
  而实际上又有人了，**这正是两条回收路径都判不出来的那个形状**（成员在另一个存储里，没有任何
  写能跨两边）。现在这次失败改为上报（`room_leave_orphan_possible`），离房照常成立：留下**一件**
  错事而不是两件。这也正是这个写变得**可丢弃**、进而才谈得上设界的原因——离房用自己的常量界住
  自己的等待，效果继续跑，因为在那里迟到落地恰恰就是想要的结果。

  这个效果是**一次** CAS，钉在「这次离房据以判定为空」的那个版本上，刻意不是
  `withVersionRetry` 循环。**对这个写来说，版本冲突不是「换个更新的版本重试」，而是
  「前提变了」。** 「是否为空」没法放进 CAS——成员在另一个存储里——所以与共享视图空房判定
  一起读到的那个版本**就是**前提；而重试循环会把冲突洗成一个更新的版本，把旧的过期时间写到
  一间刚被 join 复活的房上。那正是 #237 的隐患（reaper 删掉仍有成员的房）从后门重新进来，
  而「让效果活过请求」的期限恰好把这个窗口撑得足够大（#277 复审）。

  同样是这个宽度，决定了它必须**既钉实例也钉版本**。**版本号不是身份**——孤儿回滚早就依这条
  规则行事——而在这里它咬得更狠：一个活过请求的效果可能在「房间已被回收、代号已被重新发出」
  之后才到达 Redis，而替代房从 version 0 开始，恰恰就是「创建者从未加入过的房间」在离房时
  看到的那个版本。所以 `RoomUpdateGuard` 的实例形态带上可选的 `version`，这个调用方两者都传：
  实例说「是这间房」，版本说「自我判定它为空以来没变过」。两半各有各的回退探针，因为它们
  失败的方式不同。

  `updateRoom` 有很长一段时间两条都不满足，而这段记录值得留着，因为上面那条判据正是从它身上
  学到的。它的 CAS 比的是整份前体正文，所以迟到写不可能破坏任何东西——但它被**七个**请求处理器
  调用，其中四份成功后续不是「下一次自然覆盖」就能补回来的：加入时把一间正在过期的房间复活、
  管理侧清除共享视频的审计记录与广播，以及那两个效果必须活过请求的写。把上限放进 store 等于用
  「丢弃结果」去答复它们全体，正是有守卫的删房被搬出去的那处误放——所以第一次动手加上限被整体
  撤回了，而**判据不是「这个写是不是有条件的」，而是「上限有没有和『它成功后欠下的东西』的归属方
  放在一起」**。

  它最终能拿到上限，靠的不是对这个问题给出别的答案，而是每一个这样的调用方各自把它答完：两个
  **具名**自己的调用方一侧期限并保留效果，两个**上报**自己没能确认的事（管理侧清除共享视频两者
  都做），其余的靠同类写自然覆盖。
  上限是最后一步，也只能是最后一步。

  `createRoom` 离开名单靠的是满足后半句，而不是前半句。它的 `SET NX` 守的是**存在**而不是身份，
  所以一次在上限答复之后才落地的写**不是** no-op：它会在一个调用方已经放弃的代号下建出一间
  房——没有成员、没有 `expiresAt`，正是 reaper 永不回收的那种形状，而且因为没人持有那个代号，
  也不会有后续读去和解它。让这道上限付得起的是：它只有**一个**调用方，而这个调用方本来就拥有
  那份补偿——`createRoomForSession` 会把它可能建出来的那间房过期掉，走的是「没盖上 generation
  的房间」用的同一个 `expireOrphanedRoom`，靠的是它在发出这个写之前就生成好的代号与
  `joinToken` 来认领。**版本号不是身份**：每间新房都从 version 0 开始，所以一次手里握着
  version 0 的回滚，会和「接手了这个被释放代号的替代房」精确匹配上，把它从一个已经被告知
  建房成功的房主脚下过期掉。因此 `updateRoom` 的守卫改成 `RoomUpdateGuard`：要么是版本，
  要么是房间**实例**（`{ joinToken }`），并在「产出 CAS 守卫的那一次读」里比对——先查后做会把
  这个窗口重新打开。它是一个**形状**而不是一个可空的版本号，这样「不检查版本」就无法在不说明
  「是哪间房」的情况下被提出；那种组合会写到当前占着这个代号的任何房间上。代号复用的那条回归测试
  此前会先把替代房升到 version 1 再断言，这正是这个洞熬过 #237 与 #301 的原因。它同时不再换别的代号重试——一个不答复的存储不会因为换个代号就答复，而每
  多试一次就多留一间孤儿房。只有 `timeout` 会被补偿：`admission` 拒绝是这条连接上唯一一种能
  证明「命令根本没发出去」的答复，在那里回滚只会去写一间并不存在的房，并报告一份从未存在过的
  残留。

  **这份补偿自己也是第二条生命线，漏掉这点会让上限白设。** 它的写那一半是 `updateRoom` 的
  CAS，而 store 刻意不给它上界——所以一个直接 `await` 回滚的建房方，只是把「挂在建房上」换成
  了「挂在补偿上」，`createRoom` 的上限什么也没约束到。请求用自己的常量界住**等待**
  （`DEFAULT_ROOM_ROLLBACK_CONFIRM_TIMEOUT_MS`，既不是 Redis 的 liveness 兜底也不是删房的
  那条），效果继续跑，`closeRoomService` 在与删房链、运行时拆除同一份关服预算里排空它，并报告
  `pendingRoomRollbacks`。

  但拆开等待只是一半：**一个要继续跑的效果，不能由「带上限的调用」拼出来。** 回滚自己的那次读
  原本吃 store 的请求上限，而上限会在第一次超时时**结束这次调用**——CAS 于是从未发出，一个迟到
  落地的建房照旧留在那里。所以 `updateRoom` 接受 `boundedBy` 声明（一个**具名**的调用方一侧期限，
  而不是一个布尔），该调用走准入但不设上限，与两个有守卫的删房同形。**哪道界适用是「调用」的性质**，
  这里处处如此。`close()` 也要设闸：在关服快照之后才被受理的效果，没有人等它、也没有人报告它，
  所以 `closing` 期间要新建的回滚一律拒绝并打日志——这正是隔壁那个惰性删房遵守的同一条规则。

  把回滚**按实例**而不是按版本钉住，才让其余部分塌缩掉。回滚传的是 `{ joinToken }` 而不是版本号——与 `deleteRoom` 这么钉的理由相同：管理员
  碰一下这间还没有成员的房就会推高版本，而「版本必须一致」的守卫反而会拒掉那个正需要回滚的变化。
  由于代号换手时 store 直接答 `not_found`，循环里的重读、身份复核和那套「误报」推理全都消失了；
  剩下的只是针对一次活跃字节 CAS 冲突的有限次尝试。

  当欠下这份补偿的建房占着最后一个准入名额时，回滚仍可能在发出**之前**就被拒绝；那按残留上报，
  且不给它预留容量——准入的价值就在于它是界住 ioredis 队列的**一个**数字，而在里面开第二类
  并不会缩小那条造成拒绝的队列。

  房间存储的删房以同样的方式离开了这份名单，而且是**两个**有守卫的形态——因为守卫是
  **调用**的性质，不是方法的性质。`deleteRoom` 用 `joinToken` 钉住房间实例：管理员关房会
  先断开所有成员，他们的离房会重写记录，所以「版本必须一致」的守卫反而会拒掉引发这次变化的
  那个动作本身。`deleteExpiredRoom` 要求记录**仍然过期**，且这个判断放在同一次有守卫的写
  里——过期时间可能落在别的节点仍在使用的房间上，任何「先查后做」的排列都堵不住它。两者都是
  **一条命令**：解码正文，只比**一个字段**。不像 `UPDATE_ROOM_CAS_LUA` 那样比整份字节——
  更新不能建立在过期的正文上，而删除不能删**另一间房**，比字节把这两件事混为一谈：管理员
  关房刚断开的那些成员，其离房会重写这条记录，于是按字节的守卫会拒掉引发这次变化的动作本身，
  然后跳过运行时拆除与 `room_deleted` 广播却报成功。「先读、再按读到的字节写」有同样的毛病，
  外加判断与写入之间的裂缝。这里允许解码的理由与 sweep 相同：**不往回写**——本文件遵守的
  规则是绝不在 Lua 里**重新编码**房间 JSON。
  随后**结果**和守卫同样重要：运行时拆除与 `room_deleted` 广播都是**按代号**寻址的，所以在
  `superseded` 之后仍执行它们，作用的是现在持有这个代号的房间。`resolveRoom` 因此改为重新
  读取后作答，`closeRoom` / `expireRoom` 跳过这两步并记录 `admin_room_close_superseded` /
  `admin_room_expire_superseded`。

  **也正因如此，这两个删除都不能把上限设在 store 里面。** 一次成功的删除欠下的不止是它自己的
  答复——回收计数、运行时拆除、那条一次性的 `room_deleted`——而它们**都住在调用方**。设在
  store 里的上限，其答复调用方的方式就是**丢掉命令的结果**，于是这些后续全都静默地不再发生，
  每个调用方只好各自长出一块私有补偿：这里补一笔拆除债，那里补一次「再读一遍再广播」。#302
  的三条复审意见，是同一处放置错误的三个症状。规则就是 #282 与 #284 在下一层已经定过的那条：
  **上限只答复调用方，效果继续持有它的后续所需要的那个结果。** 所以 store 声明
  `boundedByOuterCaller`，每个调用方把「删除 + 后续」串成**一条链**并只给自己的**等待**设上限；
  迟到落地的删除照样计数、照样拆除、照样广播。`resolveRoom` 保留第三种结果：期限到达时报错而不是回答
  `null`，因为迟到的守卫仍可能回答 `superseded`，只有已确认不存在的房间才可以被报成不存在。
  **这第三种结果不上协议。** 它以 `internal_error` 抵达客户端——那是所有受界存储命令答不出来时
  本来就给的答案，也是既有码里唯一能表达「没有答案」而不宣告某个答案的。为它铸一个新码，要付出
  一次协议版本、一道面向所有旧客户端的兼容门槛和一套客户端重试状态机，换来的只是一个下次尝试
  就会自行化解的窗口；诊断应当留在日志的 `trigger` 与 `confirmation` 细节里。它**绝不能**变成
  `room_not_found`：已发布的控制器把它当作终态处理，无论待加入还是已存房间上下文都会被清空，
  于是一个根本无法证明房间不存在的结果会顺手带走用户的会话。并发读取共享该房间码唯一一个
  进行中的回收效果——真实效果只进入关服跟踪一次，请求期限只限制各自的等待，绝不能再添一层跟踪
  包装，更不能重复底层 Redis 删除。保留终局并不意味着 Redis 命令可以绕过
  队列 admission：请求读取与
  两种有守卫删除在发出前共用同一个 `maxPendingCommands` 计数，获准的命令直到真实回复才释放槽位；
  在这里被拒绝的删除从未发出，因此也没有迟到终局需要保留。加入错误会在持久化任何凭据变更前
  捕获这次请求的 generation 与完整目标，并在 `await` 后重新确认两者；旧的
  `member_token_invalid` 因而不能越过替换 socket 或较新的弹窗加入去清标记或安排重试。
  `closeRoom` / `expireRoom` 拒绝把无法
  确认的动作报成完成，返回 503
  `room_delete_unconfirmed`，而效果自己记录迟到的终局。这份所有权也延伸到关服：管理动作服务先
  关闭删除 admission，再排空已接受的 action handler，最后排空它们可能刚创建的「删除 + 后续」
  效果链；房间服务同样先关闭惰性删除 admission，再排空惰性删除及其可能刚创建的运行时拆除。
  在此期间 room store、runtime store 与事件总线都保持开放。两个所有者各自只使用一份明确预算，
  耗尽时报告剩余工作，而不是让后续依赖关闭静默截断效果。运行时拆除从重试债务账本而非请求确认
  跟踪器报告：快速拒绝或有守卫跳过可以结束后者，却留下 ownerless 债务作为已删除房间唯一的
  进程内线索。机械的那一半在
  `redis-store-command-bounds.test.ts`：挂住一条命令时，两个删除都必须**得不到答复**；而读取或删除
  占满最后一个 admission 槽位时，另一方必须在到达 Redis 前被拒绝——分类表看不见一个悄悄重新
  出现在 store 里的上限。原子的 `evictMemberToken` 不同：
  管理命令执行器只限制自己的等待并返回
  `status=error, confirmation=unconfirmed, code=block_unconfirmed`，原始 Promise 继续承载
  Redis 写入和两层本地镜像更新，再断开套接字以触发正常离房清理。最终的
  `admin_command_executed` 日志归真实
  Promise 所有，而不是归受界等待者所有，所以迟到成功与迟到失败都仍可观察。管理命令总线在
  一次已获准的发布无法再证明目标是否执行时也返回同一个附加确认标记；既有失败状态仍为
  `error`，因此滚动升级期间旧解析器仍能消费结果。Redis `PUBLISH` 明确返回零接收者时才是
  已确认的 `stale_target`。管理动作层因此审计这个有类型的确认标记，而不维护一张错误码名单；
  这是最后一个仍知道操作者身份的层。结果传输重试必须原样重发执行器结果：发布答复失败不等于
  执行失败，也绝不能抹掉其确认状态。跨节点重试之所以安全，是因为驱逐脚本保留最长封禁期限：
  即使旧尝试最后落地，两次尝试也可交换。这份所有权一直延伸到关服：consumer 会在
  unsubscribe 可能开始等待之前先关掉分发闸门，再让订阅、所有已接受的 handler，以及所有
  活得比 handler 更久的驱逐效果共享同一份关闭预算。预算耗尽时记录
  `admin_command_consumer_close_unfinished`，分别报告仍未结束的 handler 与驱逐，而不是依赖
  更晚的 runtime-store 关闭去排空一份本来属于 consumer 的效果。分发闸门不可省：Redis 总线
  可能已经在 Promise 边界后捕获了 handler；这类 handler 在关服后应答 `stale_target`，不能在
  drain 快照之后再创建新工作。运行时删房则在不截断效果轨迹的前提下拿到了界：generation
  参数变成必填，Redis 脚本不再存在通配删除；`room-service` 为每个房间 generation 保留唯一
  一条真实 teardown Promise，直到 Redis 写和每层本地镜像全部结算，因此旧 generation 的
  僵死效果不会遮住复用房间码后的清理。同一效果的所有请求等待者复用同一条确认 Promise 和
  同一个行为期限；这个期限使用独立常量，不与 Redis 连接的 liveness 常量耦合。reaper 给两条
  前置读取都传 `maintenance_pass`，继续等待真实 Promise，因此 `stalled` 仍可达。重试债只在
  创建最新 generation 效果时授予 owner（等待新尝试时则没有 owner）；复用效果的等待者可能
  带着跨过房间读取 `await` 的旧 generation，因此绝不能转移 owner；房间读取前 pin 的
  generation 还必须在该 `await` 后再次确认，确认一致才可创建或复用效果。owner 迟到成功会
  清债，owner 迟到失败会留债，两者都有最终日志。每笔 pending debt 还是一个唯一记录；
  maintenance 候选会捕获该记录的身份，并在前置等待后复核，因此 owner 在这些 `await` 中成功
  清掉的债不能被候选重新创建。新 generation 成功或观察到仍存在的持久房间会取代旧 owner，
  因此旧效果迟到的跳过或失败不能继续占着、也不能复活这笔债。
  剩下五个与在
  store 内**已经**加了上限的
  `acquireRoomLock`、`tryClaimMessageSlot` 不同：一条 `SET NX PX` 即使在调用方放弃之后
  才落地，也会在 TTL 到期时自行释放，"可能已经落地"的代价是一个锁周期，而不是一个永久
  的错误答案。

- **会过期的声明仍然有所有者。** claim 用一条 Lua 同时写入令牌、槽 TTL 与 teardown 索引分数，
  旧 tracking 写入就不能在新 owner 之后到达并覆盖它的分数。提前清理再用另一条 Lua 先校验
  令牌，同时删除槽与 teardown 索引。受界的 release 可能拖到旧 TTL 之后、且另一个节点已经
  声明同一个逻辑键之后才落地；无条件 `DEL`/`ZREM` 会抹掉新一代声明。清理也从属于
  已经确定的业务结果：它的超时要记录并吸收，不能覆盖校验、持久化或版本错误。score 与残留
  清理 cutoff 都使用 Redis `TIME`，与推进槽 TTL 的时钟保持一致；blocked-token score 仍使用
  应用时钟并单独清理。
- **豁免管的是命令，不是握手。** `connect()` 跑在 store 存在之前，且以 `ready` 收尾；
  ioredis 的 `connectTimeout` 只管 TCP 建连、不管其后的 `INFO`。两道界都没有时，
  bootstrap 会在一个"接受 socket 但什么都不回"的主机上永远等下去，所以豁免连接改用
  `connectWithin` 打开。
- **握手完成，并不代表后续启动命令也有界。** 房间事件 consumer 会在服务开始监听前
  await 第一次 `SUBSCRIBE`，所以这条命令会在独立 subscriber 连接上通过 `startWithin`
  执行。Redis 若恰好在 `ready` 之后停止应答，启动会以分阶段错误失败并断开 subscriber；
  publisher 仍不采用会破坏重试证据的兜底。handler 会在提交命令前先注册，因为 ioredis
  可能在同一次 socket 读取中先处理 SUBSCRIBE ACK、紧接着就分发消息。SUBSCRIBE 与最后一次
  UNSUBSCRIBE 共用一条串行 reconcile：后者尚未 ACK 时到来的新 handler，会先等它完成、再等
  新 SUBSCRIBE ACK，不能继承一条马上就要被移除的频道。重复注册同一个 handler 会被拒绝，
  而不是让 map 替换后遗留第一条 listener。
- **它约束的是调用方等多久，不是连接上的队列。** ioredis 会把超时的命令留在
  `commandQueue` 里以保持后续回复对齐。本仓每一道调用方侧的深度限制——
  `maxPendingAppends`、运行时存储的命令准入——仍然不可缺少，都不得因为有了这个选项而
  退役。三条采用兜底的连接会在提交前同步限制命令数；管理命令总线还会另外限制活跃的 reply
  subscription 与相应的请求闭包。该上限是会拒绝请求的安全边界，不是调度器。同一个管理服务
  内所有并发的关闭房间调用因此共用一条等待型扇出限制器，容量取 reply 上限的一半；单条
  `kickMember` / `disconnectSession` 不经过它，保留另一半容量。逐调用分批无法兑现该承诺，因为
  并发调用会把局部预算相乘。一个超时 promise 可能在命令仍留在队列时释放一个准入槽，
  但 stalled guard 最多经历自身 threshold 次失败就会重置，所以真实队列的上限是准入上限再加
  `threshold - 1`。这些连接也关闭 `autoResendUnfulfilledCommands` 与 `autoResubscribe`。
  普通命令 attempt 会绑定提交时的连接代际：reset 到 `ready` 之间拒绝新 attempt，退役 socket
  的迟到失败不得再次断开已经健康的替代连接。订阅状态的每一次变更失败都会把对应的管理
  命令总线 subscriber 代际标记为待重置，因为失败的 `SUBSCRIBE` 仍可能落地，失败的
  `UNSUBSCRIBE` 也可能留下它的唯一 channel。被拒的 `SUBSCRIBE` 尚未提交，所以不得重置健康的
  subscriber；被拒的持久订阅恢复会保持 barrier，并通过 `retry-pacer` 重试。清理用的
  `UNSUBSCRIBE` 不同：它的 channel 已经退出期望状态，因此即使准入拒绝也必须保留 reset 轨迹。
  新命令会立即拒绝；没有活跃结果时马上重置，
  否则等已经在途的结果结束后再重置，避免一次清理切断另一条命令的回复轨迹。旧代际迟到的
  失败不得重置替代它的新连接。ioredis 随后把 `commandQueue` 移到 `prevCommandQueue` 后丢弃，
  而不是在重连后重放。管理命令总线会从 handler 注册表恢复持久 command channel，也会恢复仍在
  等待答案的请求所对应的 result channel；已经结束的请求会在执行可能失败的清理之前先退出
  期望状态，所以它的 channel 不会被复活。恢复期间禁止新 publish；恢复失败则把指数
  `retry-pacer` 退避跨 `ready` 代际保留下来——ioredis 自己的计数会在每次 `ready` 清零，单靠
  它只会形成固定频率的循环。仅有 timeout 仍然没有队列界。这一条在
  `redis-client-bounds.test.ts`、`redis-admin-session-store.test.ts` 与
  `redis-admin-command-bus.test.ts` 里是验证过的，不是假设的。
  采用调用方界的房间事件 publisher 则是互补形状：它的提交准入会一直占槽，直到真实的
  Redis `PUBLISH` 结算。`firePublishRoomEvent` 的包装器超时不能重新放开该槽；普通事件、
  一次性 resync、reaper 通告和管理端发布都会经过同一条总线级真实命令上限。
  `redis-room-event-bus.test.ts` 固定了这项性质。
- **分不清"慢"和"死"的阈值是要避免的失败。** 它被放在普通时延之上很远，因为在"只是
  落后的 Redis"上跳闸，会一次性把每条连接上的降级依赖变成失败依赖。
- **有界了仍然欠一份上报。** 命令开始失败的连接欠调用方的是一个诊断而不只是一个错误：
  僵死的会话存储答 503 `admin_session_store_unavailable`——绝不能是 401，那会读作一次
  登出；房间/运行时存储的超时与准入拒绝则答 503 `room_store_unavailable` /
  `runtime_store_unavailable`，不能落进兜底 500。这套翻译是 HTTP 边界共享的一条策略：
  管理路由与独立 metrics server 都复用它，因此把 `/metrics` 移到单独端口不能把同一次
  依赖故障重新降级成没有诊断的 500。会话路径另记
  `admin_session_store_command_failed`，带上响应对未认证调用方隐去的 Redis
  细节。guard 等待 `ready` 期间被拒的请求也走同一上报路径。被 publisher 准入拒绝的 executor
  结果从未成为 Redis 操作，因此不得虚增 Redis failure counter；最终结果发布回调会在诊断日志
  被节流之前，无条件增加 `bili_syncplay_admin_command_result_publish_failures_total`。它表达的是
  executor 未能完成发布路径，不是断言送达一定丢失：超时的 Redis `PUBLISH` 仍留在队列中，
  Pub/Sub 也不提供 requester 收件回执。
- **同一条连接上的清理不是答案。** 当一个请求用同连接上的命令把真正的工作夹在中间时，
  这些清理的 reject 不得替换掉结果：否则管理命令总线 `finally` 里的 `UNSUBSCRIBE` 会
  把僵死本该产出的 `command_timeout` 结果抛掉。但清理也不能就此忘掉：清理失败会标记
  subscriber 待重置，先保护已经在途的回复，之后再恢复持久注册表。去重槽 rollback 遵守
  同样的先后关系：记录清理失败，但保留触发清理的原始业务错误。

## 测试夹具不得把类型检查绕过去

每个包的 `test/**` 都在 `npm run typecheck` 范围内——否则一次漏改了某个测试调用点的签名变更会悄悄通过这道门，
并可能顺带掩盖掉那个漏掉的参数所造成的行为回归（`#210` / `#211`）。
各个包如何满足这一点，取决于它的 src 与 test 能不能共用一套编译器配置：

- `protocol`、`server`、`extension` 需要第二个 project，因为它们的测试需要 `node` 类型
  （以及 `server` 对 `bench/` 的引用），而 src 构建不能带上这些。它们的 `typecheck` 先跑 `tsconfig.json`，
  再跑 `tsconfig.test.json`。
- `admin-ui` 不需要第二个 project：它的 `tsconfig.json` 本就包含 `test`
  （其 src 是由 Vite 编译的浏览器代码，因此无需拆分）。

新增的包按适用的那一种来选——不要为了"和多数保持一致"而添一个不必要的 `tsconfig.test.json`。

保持夹具诚实，不要用类型断言绕过检查器：一个不再符合其类型的夹具，通常意味着类型动了
（字段被改名、被删除，或变成了必填），修改的位置就在夹具里。
以下三类断言尤其要避免，因为每一类都会重新打开这道门本想关上的缺口：

- 对夹具使用 `as unknown as <DomainType>` / `as never`（`RoomState`、`PlaybackState`、`Session`、`RoomStore`）——
  它压掉的正是你想看到的"缺少必填字段"错误。
- 用 `as T` 让桩满足一个无约束的 `<T>(…) => Promise<T>`。没有任何值能栖居于每一个 `T`，所以这个断言是无条件的。
- 让桩满足一个把若干组请求/响应塞进同一个全可选响应类型的契约。此时 `{}` 满足一切，也就什么都没检查——
  `#211` 曾经犯过一次这个错误才发现它。

当一个回调只服务于一组请求/响应时，就声明那一组。当它服务于多组时，把它拆成每组一个回调
（`sendPlaybackUpdate` / `requestRoomStateHydration`），而不是放宽响应类型。
当载荷确实无法建模、且无论如何都要在运行时用守卫收窄时，就声明 `Promise<unknown>`，交给守卫去收窄。
如果某个消费者只用到一个大接口的一部分，它的参数就应当如实写出来（`Pick<RoomStore, "countRooms">`）——
这样假实现根本不需要断言。

对于确实无法伪造的平台/库对象（`ws.WebSocket`、`chrome.tabs.Tab`、`HTMLVideoElement`、`IncomingMessage`），
`as unknown as T` 是可以的；优先写一个共用的构造函数，而不是在每个调用点各断言一次。
