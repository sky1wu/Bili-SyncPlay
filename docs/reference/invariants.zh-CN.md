# 运行时不变量

以下规则没有任何类型、lint 或测试能独立保证，每一条都是某个 bug 或某轮漫长复审用代价换来的。
[AGENTS.md](../../AGENTS.md) 收录每条规则的一句话版本；本文收录背后的推导——那才是你动这些代码之前需要读的部分。

改动后台播放计时、共享归属、共享运行时存储、房间事件广播或后台定时任务之前，请先读对应章节。

英文版见 [invariants.md](./invariants.md)。

## 播放计时不变量（Playback timing invariants）

其中三条在 #210 上合计花掉四轮复审。类型系统对它们一概无能为力，所以每当某条后台路径触及房间状态或播放计时时，都必须人工核对。

- **绝不用服务端时刻减本地时刻。** `serverTime` 属于服务端的钟，本地时刻属于本机的钟。两者之差是钟差，
  它不是时长，而且会自行漂移——接收端拿它当目标，播放倍率就会永远摆动。请改用本地单调锚点外推播放位置
  （`clock-controller`）；跨机器传递"过了多久"时，传的必须是**时长**，绝不是时刻。两个服务端时刻互相比较没问题
  （版本排序），两个本地时刻互相比较也没问题（流逝时间）。

- **快照的 age 在每次发送时现算，绝不存储。** `room:state` 携带 `playbackAgeMs`，好让中途加入的客户端知道
  手里这份快照已经陈旧了多久（服务端的 `withPlaybackAge`，接收端的 `resolvePlaybackAnchorAtMs`）。
  age 只在它被发出的那一刻为真，所以一旦存下来它就退化回时刻——这正是它挂在 `room:state` 载荷上、
  而不是挂在 `PlaybackState` 上的原因：后者是服务端持久化、客户端又回传的那个结构。
  每一处 `room:state` 发送点都必须打上它（共四处：bootstrap、`sync:request`、以及 `room-event-consumer` 里的两处），
  扩展端则在状态进入存储或被 member-delta 重新包装之前把它剥掉。

- **播放快照的到达时刻，必须记录在快照可被观测之前。** 一旦它写进 `roomSessionState.roomState`，
  正在重新水合的内容脚本（`content:get-room-state`）就能读到它，成员的加入/离开也能把它重新包装；
  而谁先做补偿，谁就会把它锚在**自己**的那一刻上，丢掉房间在此之前播过的一切。
  `markPlaybackArrival` 必须在写入之前、且在任何 `await` 之前执行。把 socket 消息串行化并不能覆盖这一点：
  那些读取方走的是 `chrome.runtime` 通道，不是 socket。

- **每个 `await` 之后，先确认手里的房间状态仍是当前的，再做补偿或投递。** 处理器是按 socket 消息逐条以
  `void handleServerMessage(...)` 启动的，彼此不串行，所以某个处理器在 await 期间（`ensureSharedVideoOpen`
  可能要开一个标签页）新状态可以后来居上。被取代的快照必须丢弃而不是投递：内容脚本的陈旧判断是按 actor 做的
  （`lastAppliedVersionByActor`），因此一份来自**另一位成员**的、已被超越的快照会被接受，并把播放拉回过去。
  `handleRoomStateMessage`、`applyRoomMemberState`、`expireBootstrapRoomStateWait` 各自都带着这道检查；
  新增的投递路径需要自己那一份。

- **凡是代表"这不是用户干的"的标记，都必须以它自己的窗口去问手势，且不得开任何例外。**
  `lastUserGestureAt` 是内容脚本判断某次导航/暂停是否出自用户的唯一证据，而 `userGestureGraceMs`（约 1.2s）
  是错误的询问跨度：任何窗口比它更宽的标记，都存在这样一段空隙——用户的手势已被遗忘，标记却仍读作新鲜。
  要问的问题是"这个手势有没有可能就是我眼下所见的成因？"，所以跨度必须取标记自己的窗口——
  既然它肯为一个倒计时等上 10s，就同样欠一次慢解析的 SPA 点击这份耐心。

  **该跨度锚定在标记自己的时刻上，而不是 `now`。** 让手势从 `now` 开始计龄、标记却从自己的时间戳计龄，
  会在尾部留下一条缝：标记仍然有效，手势却刚好过期。标记对 `[mark, mark + window]` 区间内的事件有效，
  而可能造成其中任一事件的手势落在 `[mark - window, now]`——所以跨度就是它，`now` 从判断中彻底消失。
  它的下界在另一个方向上同样吃重：没有下界的话，在一集 24 分钟的开头按下播放，会永久否决这一集的自动连播。

  **在该跨度内，每一个手势都推翻标记，没有例外**——尽管确实有些手势与标记并不矛盾：分享者把进度拖到最后几秒，
  其后真的会发生一次自动连播。#236 为了恰好放行这一个手势花了五轮复审，而每一次修复都在两种失败之间来回摇摆：
  放行手动选集点击（分享者把自己的私人选择推给了整个房间），或者误判一次真实的拖到片尾（房间悄无声息地不再推进）。
  信号无法区分二者——两者都是离散输入，一次点击可以落在 `seeking` 与 `seeked` 之间，
  而一次拖拽自身的松手 `click` 晚于开启它的 `pointerdown`。所以规则取那个笨办法，代价则写成一条测试记下来
  （"...the accepted cost of having no gesture exception"）：拖到片尾的分享者，手动分享下一集，仅此一次。
  重新引入例外，就是重新打开那场摇摆。

  整套方案之所以安全，是因为 `lastUserGestureAt` 只由**离散**输入刷新（`gesture-tracker.ts`：
  pointerdown/mousedown/click/touchstart/keydown/popstate），绝不由指针移动或滚动刷新——
  记录后两者的追踪器会把被动观看变成一票否决，从而悄悄废掉这个标记。

  **一次性标记必须被消费，而不只是被设期限。** 能推翻它的证据比它自己更短命
  （`resetUserGestureState` 在每次导航时把 `lastUserGestureAt` 清零），所以一个活过了它所解释的那次导航的标记，
  会在反对者已经消失的情况下再获得一次机会。请在处理器开头把它读进局部变量并清除。

- **被两种行为共用的窗口常量，其实是两个常量。** `INITIAL_ROOM_STATE_PAUSE_HOLD_MS` 曾同时是
  "页面加载自动播抑制多久"和"自然结束标记的有效期多长"（#236）。两者之间毫无关联，
  于是后者被悄悄钉死在一个为前者挑选的数值上——而 3s 短于 B 站约 5s 的下一集倒计时，
  这让标记在它本要捕捉的每一次自动连播之前就已过期。当一个常量被第二处调用点以不同的问题读取时，
  就把它拆开，并写明各自是以什么为度量。回归测试需要断言的那些数值放在
  `extension/src/content/timing-constants.ts`，而不是 `content/index.ts`：
  一条自己重新抄写数值的测试，在别人改掉线上那个数值之后，照样通过得心安理得。

## "地址栏是否标识在播视频"是路由自身的属性

在内容脚本眼里长得几乎一样的两类 B 站页面，对这个问题的答案正好相反。极性套反了不会得到
一个"降级的答案"，而会得到一个"自信的错答案"，#274 就是它的代价：页内切集之后，房间的共享
视频一直钉在上一集——却带着**新一集**的进度，于是其他成员反复被拉回上一集开头——直到分享者
刷新页面才恢复。

- `/festival/<id>` 在播放器走完整个播放列表的过程中，路由与打开时带的 `?bvid=` 都不会变。
  那里的地址栏是 {@link isAddressBarOpaqueVideoUrl} 意义上的"不透明"：page-bridge 快照是
  唯一的身份来源；而且一旦解析成功过一次，地址栏就被**证明**为陈旧，其解析结果不得再用作
  兜底（否则会答出"另一个非共享视频"，把页面强制暂停）。
- `/bangumi/play/ssNNN` 标识的是季，从不标识具体某一集，所以同理由快照优先。
- `/bangumi/play/epNNN` 标识的就是这一集本身。切到另一集必然改变它——页内切集走的是
  `pushState`——而且**地址栏先动**，`__INITIAL_STATE__`、`__playinfo__`、分集列表高亮项都在
  它之后才跟上。所以在这里，可能陈旧的恰恰是每一个页内来源，不可能陈旧的恰恰是地址栏。

于是在 `ep` 路由上规则整个反转，`contradictsAddressBarEpisode`（`video-identity.ts`）是陈述
这条规则的唯一判据：

- **快照报出别的一集，含义是"还没解析出来"，不是"解析好了"。** 返回 `null` 才让
  `resolveCurrentSharePayload` 的 8 次重试真的跑起来——它的退出条件是"拿到非 null 快照"，
  所以加闸门之前，第一次陈旧读取就返回了，剩下 7 次一次都没跑，哪怕页内全局在第 2 次读时
  就已经更新。最坏情况这时退化成"用地址栏解析"，而不是"分享上一集"。
- **`ep` 路由绝不能被记为"地址栏身份已被否证"。** `rememberSnapshotResolved` 由
  `isAddressBarOpaqueVideoUrl` 把关，而后者只认 festival，正是为此。否证它等于把错答案钉死
  到这个页面生命周期结束为止——这恰好就是用户报的"只有刷新才恢复"。
- **要否证整条陈旧记录，而不是被比对的那个字段。** 高亮列表项和页内全局一样滞后于切集，
  所以当它的 ep id 与地址栏矛盾时，它的标题和 cid 同样是陈旧的：标题会挂到新一集的身份上
  发出去，cid 会匹配上上一集的缓存快照。
- **矛盾会沿着"匹配关系"传递。** 高亮项常常根本不带 ep id（很多分集列表只给 `data-cid`），
  它无法自证陈旧；但一份与它相匹配（ep id / cid / 标题任一相同）又与地址栏矛盾的快照，
  已经代它证明了它属于上一集。此时只拒绝快照会留下一条混合记录：地址栏的 `ep396139`
  披着上一集的标题。矛盾波及到哪里就作废到哪里，而且作废的是整条记录，不是当下这个调用方
  恰好读取的那个字段。
- **两侧都必须已知。** `bvid:cid` 快照根本不标识某一集，季路由也不标识；在未知项上否证是
  猜测，不是矛盾。

让这个 bug 得以出厂的覆盖缺口值得当作警示抄下来：`share-controller.test.ts` 里所有 bangumi
用例走的都是 `ss` 季页，而在那里"快照优先"是对的，于是这条规则被跨极性套用却无人拦截。
其中一类路由的回归用例，对另一类什么都不能证明。

## 共享归属是推导出来的，而增量消息并不携带它

`sharedVideo.sharedByMemberId` 只在 `video:share` 时写入一次，它是一个指向易变身份（分享者的席位）的持久引用。
#235 就是它悬空之后的样子：没有人算得出 `isLocalSharedSource()`，于是没有人推进房间。
三条规则维系着它，没有一条由类型保证：

- **在构建时求解，绝不回写房间。** `roomStateFromSessions` 是 `sharedVideo` 抵达客户端的唯一出口，
  也是把存储的 id 与在线成员名单对账的唯一地方（`resolveSharedVideoOwnerId`）。
  新增的 `room:state` 构建点必须走它。持久化的房间刻意保留原始 id：那是**首选**归属者，
  所以一个只是网络抖了一下的分享者会在重连后夺回共享，而不是就此永久失去它。

- **完整的 `room:state` 只能在索引可证已清理干净的地方发布。** 换房时旧房间是在
  `createRoomForSession` / `joinRoomForSession` 内部离开的，而 `releasePreviousRoom` 会报告 `onRoomLeft`
  是否真的清掉了索引。`room_member_left` 增量消息无条件发出——它不读任何状态——
  但完整状态只在换房者回不来的地方发布：`publishPreviousRoomResync` 手握两张许可证之一即可，
  一是新的加入已经落座（它的写入会以**新**房间码重写整条会话记录），二是 `onRoomLeft` 本身已经落地。
  即使加入被拒，旧房间仍欠它一份状态，凭的是第二张许可证——因为回滚只撤销新房间那一侧。
  "会话哈希里已经写着新房间码"不是可以假定的事：那个哈希正是由 `onRoomLeft` 自己写的（#242）。

- **一条移动了归属的成员增量消息，欠房间一份完整的 `room:state`。**
  协议 >= 2 的客户端收到的是 `room:member-joined` / `room:member-left`，它们只编辑接收方的成员名单，
  别的什么都不改——接收方缓存的 `sharedVideo` 仍然指着上一份完整状态所指的那个人。
  `leaveRoom` 在 `needsRoomStateResync` 时额外发布一次 `room_state_updated`；加入路径同理：
  当新加入者在刚发给它的 bootstrap 状态里恰好是共享归属者时，也补发一次。
  这两处判断都不得替换成依据 `joinedAt` 排序的捷径：该值由处理这次加入的那个节点打戳，
  所以那是一次跨节点的钟比较，可能把成员顺序颠倒过来。任期规则的存在只是为了让归属不要每来一个人就重排，仅此而已。

- **一次离开在 `onRoomLeft` _成功_ 落定之前，不得发布任何 `room:state`。**
  该钩子把会话从房间索引里清掉，而 `getRoomStateByCode` 读的是索引、不是成员表——
  所以在写入仍排队时、或写入失败之后构建出的状态，会包含那位刚刚离开的成员，并把共享原封不动地还给他。
  `runRoomLeftHook` 是被 await 的，并会报告是否成功；app 层的实现会 await `runtimeStore.flush`。
  `room:member-left` 不受此限，失败时照发：它不读状态，所以脏索引污染不了它。

  除显式离开之外还有两条路径需要同样处理，而且都容易漏，因为在它们身上"离开"并不显眼：

  - 换房的成员是在 `createRoomForSession` / `joinRoomForSession` 内部离开旧房间的，
    而这两个函数自身什么都不发布——所以两个处理器分支都要自己释放旧房间。
  - 同样这两个调用，是在它们**可能失败之前**就离开了旧房间的（房间满、加入令牌错误、准入锁超时、房间码冲突）。
    `enterRoom` 在这条路径上也要释放旧房间，并以 `session.roomCode` 确有变化为守卫，
    否则一次根本没走到"离开"的失败会广播出一个成员从未离开过的房间。

## 运行时存储是写回式的，所以"排空"从不等于"写入成功"

`registerSession`、`markSessionJoinedRoom`、`markSessionLeftRoom`、`unregisterSession`
会同步更新本节点自己的表，并把共享写入排在其后。
下游凡是"写入、读回、然后据此做决定"的地方，都必须清楚自己问的是这两个问题中的哪一个（#242）：

- **`flush()` 说的是队列空了，`confirmWrites()` 说的才是写入落地了。**
  `flush` 等的是吞掉了错误的副本，所以一次失败的写入排空得与成功的写入一模一样。
  当重点在顺序时用 `flush`（"我自己的写入对我接下来要做的读是可见的"），当重点在持久性时用 `confirmWrites`。
  `confirmWrites` 是全存储范围的，并且会清掉它所报告的内容，所以答案的含义是"自你上次询问以来"；
  只需要确认**自己那一次**写入的调用方应当直接 await 那次写入，因为这四个函数都会如实报告各自的结果。

- **排队的写入会带退避重试，而一次重试可能活得比它的房间更久。**
  `durable-write-queue` 给每一次排队写入一份有界、带退避的重试预算。
  这重新打开了 #237 关掉的房间码回收风险：一次在房间码易主之后才落地的重试，会写进新房间。
  只有加入写入会把会话**加进**房间，所以只有它需要这道守卫——而且那枚 pin 是在 `markSessionJoinedRoom`
  **被调用时**读取的，绝不在可重试的函数体里读：函数体要等该会话的链条排空之后才运行，而排空是无界的，
  所以在那里取的 pin 可能已经指向这个房间码的**下一位**占用者，检查便直接放行。
  不匹配即 `NonRetryableWriteError`（代（generation）只会向前走，所以后续任何一次尝试都不可能绕回来）。
  代读不出来时宁可拒绝这次加入，也不留到以后再读，因为第二次读就是第二次钉错实例的机会。
  代**不存在**时仍然 pin 成 `""`，这正是拆除流程在那个键里留下**墓碑**而不是删除它的原因：
  删除会让"已拆除"与"从未打戳"变得无法区分，于是一枚 `""` 的 pin 就匹配上了它正要复活的那个房间。
  墓碑**不设过期**——TTL 必须活得比任何可能仍持有旧 pin 的写入都久，而这些写入没有上界，
  所以一个失效的墓碑会让 `""` 的 pin 再度匹配上一个不存在的键。回收墓碑的是下一位占用者的 `markRoomGeneration`。
  对墓碑**本身**取 pin 会被拒绝，否则一枚在拆除之后取的 pin 就会匹配上它。
  `hasRoomResidue` 忽略该键，所以墓碑绝不会让一个房间码一直被占着。
  任何按房间码落座或迁移数据的新写入都需要同一枚 pin；只碰以会话 id 命名的键的写入则不需要，因为会话 id 从不复用。

- **每一份重试预算，都要对着排空它的那个关闭步骤来配。**
  `close_shared_runtime_store` 与 `flush_pending_room_event_publishes` 各自带显式超时，
  超时会以 error 级别记录并报告为**降级（degraded）**步骤——于是一次仅仅因为等完重试而超时的关闭，
  会丢掉本来可以落地的写入（但**不会**让进程以非零码退出，见下面第三条 DEGRADED 规则）。
  `close()` 会先调 `stopRetrying()`，它会截断正在退避中的等待，**并且**丢弃尚未开始的写入，
  最多只留下**一次**在飞的尝试；步骤预算必须大于那一次尝试自身的超时。
  调高 `maxAttempts` 或任何一个延迟，都意味着要重做这套算术。

- **重试的节奏住在 `retry-pacer` 里，不在各个设施里。**
  退避排程、可被关闭打断的等待、不取消调用的单次尝试上限、以及对活过上限的调用的记录，
  是由 `durable-write-queue`、`pending-resync-queue`、`runtime-index-reaper` 和存储的命令包装器
  共用的**同一份**实现。它们曾是四份手写副本，而 #242 的复审意见里有六条是同一个缺陷出现在
  上一轮没碰到的那份副本上。新增的重试设施用这个 pacer，不要长出第五份副本。
  留在本地的是真正各不相同的部分：顺序/取代/确认、去重，以及由谁来决定重试。

- **跑光了预算的关闭步骤是 DEGRADED，不是 failed。**
  只有抛出异常的步骤才让进程以非零码退出（`graceful-shutdown.ts`）。
  这些预算之所以存在，正是因为这些步骤在等本进程无法取消的 I/O，所以"放弃等待"本就是设计中的结局。
  把超时当成失败，会把每一句"万一这个调用挂住了呢？"都升格成正确性主张——
  而这个问题没有最后一个答案，因为每加一道有界等待去回应它，那道等待自己又成了可以被同样发问的新调用点。
  #242 有十条复审意见都是这同一个问题的反复重提。两种结局仍然都以 error 级别记录；放弃排空这件事必须保持可见。

- **超时是答复调用方，它不取消命令。** 这一条在三个地方咬人，而修好其中一个不等于修好了它：
  - 会话的键，要等这次写入所启动的每一条命令真正结束之后才释放（`DurableWriteRequest.settle`）。
    在调用方被答复时就释放，会让补偿写入——它排在同一个键上——先跑，
    于是那条被放弃的命令落在它自己的回滚之上，留下一个客户端被告知并不存在、却能把共享赢回去的成员。
    `drain` 会等这些释放；`confirm` 刻意不等，因为一条仍在飞的命令早已给出过它的判定。
  - 没有任何地方会在第一次调用尚未答复时启动第二次——写入队列不会，`pending-resync-queue` 不会，
    reaper 的按房间发布也不会。否则一个挂住的依赖会按重试次数累积在飞命令。
  - 没有任何地方会在有在飞调用时关闭连接或总线：`close()` 先（有界地）排空链条再 `quit`，
    resync 的排空则先（有界地）等完那些被放弃的调用，之后关闭流程才关掉总线。

- **当同一会话有更新的写入排队时，重试就此放弃。** 越过这个点继续重试，是在和更新的写入较劲。
  这一点之所以成立，是因为加入写入重写的是**整条**会话记录，而不是只打补丁改 `roomCode`——
  于是一次丢失的 `registerSession` 会被下一次加入修好，而不是留下一个没有 `id` 的哈希，
  那种哈希会被 `loadSession` 读成"根本没有会话"。
  任何只携带记录严格子集的新增会话写入，都不得指望更早的那次写入已经落地。

- **索引写入失败的加入是中止，不是落座。** `runRoomJoinedHook` 会报告失败，
  处理器随即以 `leaveRoom(session, "disconnect")` 回滚这次加入——用 `"disconnect"`，
  是为了让重连的成员保住共享归属规则所依赖的那个身份。
  加入之后要发的一切都是从这次写入所维护的索引里读回来的，所以一个房间看不见的成员，
  比一次客户端会重试的加入失败更糟。而如果**回滚**也失败，就断开 socket：
  `leaveCurrentRoom` 在自身持久化失败且 socket 仍开着时会把成员恢复回来，
  所以在服务端仍占着席位的情况下告诉客户端加入被拒，会让两边就此各说各话。

## 一次性广播需要重试轨迹，重复发送的则不需要

几乎每一条 `room_state_updated` 都会被下一次 `video:share` / `playback:update` / `profile:update` 重发，
所以丢一条只值一瞬。有两条是一次性的，一旦总线拒收，它们就永久丢掉这个房间（#242）：

- **共享归属 resync**（`publishSharedOwnerResync`）之所以触发，恰恰是因为房间已经停止推进，
  所以它后面什么都不会跟着来，而空闲的房间也不会发 `sync:request`——只有刷新页面才能恢复。
  它走 `pending-resync-queue`：该队列在一个立即返回的 `request` 背后带退避重试；
  `firePublishRoomEvent` 刻意不 await 它的包装器，而让离开/加入处理器阻塞在总线上会是更糟的取舍。
  一条记录会一直重试到总线收下为止——给单条记录设尝试上限，只是用更慢的方式丢弃一条没有别的东西会重发的通知——
  所以 `drain` 按设计是无界的，关闭时的调用则传 `{ final: true }`，它会先调 `stopRetrying`，
  最多留下一次在飞的尝试去等。一条记录在它的第一次发布尚未答复时绝不启动第二次：
  尝试上限是在和总线调用赛跑，并不能中止它，所以一个跑在挂住的总线之上的无界重试循环，
  否则会按重试次数堆起一条条在飞的 Redis 命令——和写入队列 `settle` 那条"超时不等于取消"是同一套推理。

- **运行时索引 reaper 的通告**，是唯一能告诉房间"某个死掉节点上的成员已经不在了"的东西。
  一旦本轮扫描清理完索引，`listClusterSessions` 就不再返回那些会话，
  于是之后的扫描再也没有任何线索能重新发现那个房间。
  reaper 自己保有一份记录集合，并在**每一轮扫描的开头**重试它——在"没有离线节点"的提前返回**之前**——
  只有发布成功才丢弃一条记录。这个队列和 `pending-resync-queue` 都不给积压设上限：
  驱逐或拒收一条尚未发布的记录，丢掉的正是它们存在的意义，所以积压只记录、绝不丢弃。
  正因为无界，每一条经过它的**关闭**路径都必须有界，而这样的路径有两条：
  `stop()` 以有界并发对着自己的截止时间排空，并且它在 await 在飞的那轮扫描**之前**就先置上 `stopping`，
  好让那轮扫描的串行排空及时让路，而不是先把整个积压跑完。只给第二条设界，预算照样会被打穿。
  超时的步骤会被大声记录下来，**并且**会让总线在有在飞发布时被关掉，而这些发布随后会像已经落地一样删掉自己的记录。
  每一次发布自身也有上限：一个只决定"要不要开始下一条记录"的截止时间，在总线是挂住而不是拒收时什么都界不住。
  扫描之间也不再重叠：它们共用那份集合，而 `stop()` 只 await 它知道的那一轮扫描。

  记录是怎么产生的，是这件事的另一半：一个房间只有在**那条**会话的清理写入被确认之后才会被通告，
  而会话记录正是重试得以可能的前提。扫描的各个步骤按它们所摧毁的东西排序——
  移除成员需要 `roomCode` 和 `memberId`，`markSessionLeftRoom` 会把 `roomCode` 抹掉，
  `unregisterSession` 会删掉整条记录——所以每一步都只在前一步被确认之后才运行，
  而没能落地的步骤（失败、被上限截断，或被 `stop` 打断）会把记录原样留给下一轮扫描从头再做一遍。
  每一步都是幂等的，这正是重做它不花钱的原因。#235 曾用相反的方式回答这个问题——它无条件通告，
  理由是 `unregisterSession` 反正会清掉同一个键，而设门槛"会让下一轮什么都没得重试"——
  这套理由只在扫描无条件执行 unregister 的前提下成立。
  `unregisterSession` 是唯一一处不被任何东西设门槛的写入，因为它返回 `void`
  （所以 `confirmWrites` 是唯一能看到它结果的地方），也因为它失败时房间索引本就已经干净，
  下一轮扫描重跑一次也不过是空操作。

## 不能超时的后台轮次，也就无法被观测

`room-reaper`、`room-index-reconciler` 与 `node-heartbeat` 每次触发都对 Redis 跑一轮异步任务。
这条链路上原本没有任何超时，两个 Redis 客户端也都没有——`lazyConnect` 与
`maxRetriesPerRequest: 1` 约束的是重试次数，而不是 Redis 已经收下的那条命令可以花多久回应。
于是连接半开时一轮任务会永久挂起，reaper 不再回收过期房间，却**没有任何**信号：
`bili_syncplay_room_reaper_sweeps_total` 的两条序列一起静止，只看失败率的告警不会触发，
恢复只能靠人工重启（#261）。心跳坏得一样、后果更重：`node_heartbeat_failed` 只能通过那一拍的
`.catch` 抵达，所以一拍永远不 settle 就什么都不会记，与此同时其他节点把它从集群索引里判老、
回收它的 session——而它还在服务客户端（#263）。
下面这些规则统一放在 `maintenance-pass.ts` 里——一份驱动，因为同一个缺陷在每一份手写副本里都出现了：

- **每一次触发都恰好记下一个结果。** 只有这样，"速率变平"才只能意味着"定时器没了"。
  超过上限的一轮记为 `error`，而不是沉默。如果上限只报告**第一次**僵死的触发，
  僵死持续期间序列又会重新安静下来——那不过是把原来的 bug 多绕几步。
  但"记下来"不等于"算失败"：发现上一轮还在上限**之内**跑着的那次触发，有自己的
  `skipped` 标签——间隔是个只要求为正整数的配置项，完全可以被设得比上限还短，
  把它记进 `error` 会让一个正在正常回应的依赖把失败率顶到 1（#262 复审）。
  于是 `stalled` 必定跟在同一条调用的 `timed_out` 之后——runbook 就是这么教运维读它的。
- **上限不取消调用，所以一轮绝不叠在另一轮上面。** 没有任何东西能中止已经发出的 Redis 命令，
  上限只是让调用方不再等待。上一条命令尚未回应就再次触发，会按每个周期一条的速度堆积命令；
  而且——因为关服步骤等的是**最后**一次触发存下的 promise——会让关服在等最新那一轮，
  更早的几轮却还在写。同样的推导见 `pending-resync-queue` 与 runtime index reaper 的逐条发布上限。
  占位是由调用自身的回应释放的，不是由上限释放：晚一跳释放会把下一轮判成 `still_running`，
  直接把扫描速率砍半。
- **`stop` 要等真正的调用，但要有界——预算不够时还要说出来。** 下一个关服步骤会关掉 Redis 连接，
  所以命令还在空中就返回等于和 `redis.quit()` 赛跑；但无界等待只是把超支挪进关服步骤，
  然后那一步被记成失败。`retry-pacer` 的 `settleTracked` 就是这个有界等待，
  其预算必须留在该步骤自身的超时之内。而"悄悄放弃"是同一笔交易的反面：
  这场赛跑原本**正是因为**那一步超时才被看见，所以干净返回的 `stop`
  欠调用方一条 `onSettleTimeout`，把仍未回应的调用数报出来。
  在同一次改动里既给等待加了界、又把它的信号丢掉，正是"治沉默的修复在下一步重新制造沉默"的做法。

- **上限是由"这一轮迟到要付什么代价"推出来的，不是拍脑袋图省事定的。**
  reaper 是固定 30s（默认间隔 60s）。心跳则是算出来的（`heartbeatTimeoutMs`）：半个间隔，
  且不超过 `NODE_HEARTBEAT_TTL_MS` 的三分之一——因为一拍迟到的代价是别的节点在 `staleAt`
  把它判老、在 `expiresAt` 回收它的 session。上限如果跟过期同时触发，那就是在回答一个
  已经没人能据此行动的问题。"低于间隔"是这条规则的另一半：正是它让超时之后的那次触发
  是 `stalled` 而不是 `overlapped`。

上限属于调用方，不属于连接：房间存储与 runtime store 的客户端都仍然没有 `commandTimeout`，
命令本身照样挂在 socket 上。尤其 `heartbeatNode` 是直连的 `MULTI`——它不走写回队列，
所以队列自己的 `pendingOperationTimeoutMs` 从来就没管到它。
在那里加超时会连带约束请求路径（`get_room` / `update_room`），那是另一个需要单独权衡重试语义的决定——
#261 有意没有做。

## 无界的写入队列会把"僵死的依赖"变成"还在增长的依赖"

`redis-event-store` 把每次 append 串在一条 promise 链上，让 stream 的顺序与事件顺序
一致。但这条链上没有任何一环有上限，而喂它的是**每一条**结构化日志——于是第一条永不
返回的 XADD 之后，后面每条日志都变成又一个闭包，各自捕获着自己的事件正文，既没有上
限也没有去重。只要 Redis 一直僵死，内存就随日志速率增长；`queryEvents` 等在同一条链
上，后台概览的每个计数也是；`close()` 是 `await pendingAppend`，因而必然超出
`close_event_store` 的预算（#264）。规则如下：

- **不能拒绝工作的队列，不受任何东西约束。** 单次写入的上限与队列深度上限回答的是两
  种不同的故障，互相不能替代：上限在 Redis 不再回应时触发，深度上限在 Redis 回应得
  比事件产生得慢时触发——后一种状态下任何上限都不会触发，而队列会一直长下去。两者
  缺一不可。
- **在这里丢弃是对的取舍，在别处不是。** 事件流是可观测数据，它自己还带着 `MAXLEN`；
  丢条目的代价是列表不完整，而丢弃计数会把这件事明说出来。这与 `pending-resync-queue`
  正好相反——那里丢了就是永远丢了，见
  [一次性广播需要重试轨迹](#一次性广播需要重试轨迹重复发送的则不需要)。
- **把故障报成事实，不要报成"一次事故"。** 第一版把它报成有起点、有终点、有总量、
  原因还会升级、且有两种终结方式的一段"事故"。随后 #266 用四轮复审找出了配对断掉的
  各种状态：节点流量安静下来、关服抢先到达、写入以拒绝告终、阶段变化多打了一个起点、
  终点被调高的 `LOG_LEVEL` 滤掉。这不是运气差。起止配对就是一个 span，span 带着不变量，
  而日志流里没有任何东西能保证不变量——尤其是在"依赖正在坏掉"的那个组件里，于是那个
  依赖的每一种失败形态,都是配对断掉的又一种方式。`maintenance-pass` 能用同一个形状，
  只是因为定时器保证了每一拍离散且必然结束；**模式的保证来自它的前置条件，不来自它的
  形状**，而 append 路径是调用方驱动的连续流，两者都继承不到。取而代之的是：按原因限流
  的一行"正在发生什么"，外加一个计数器——而"还在不在发生"和"发生了多少"，计数器从第一版
  起就无状态地答对了，一条意见都没挨过。
- **上报不得依赖它所上报的那个东西。** 这些行经 `logEvent` → `eventStore.append`，
  于是上报与它正在上报的容量互相争抢，生出自反回环、日志级别路由问题，以及容量边缘
  每完成一次写入就抖一次。一个错误的依赖方向，贡献了四条意见。`logger.ts` 把"排除出
  store"与"固定 error 级"放在一起，因为它们是同一个原因。
- **被丢弃的 append 仍然成功地答复调用方。** 调用方是结构化日志器，它会把一次拒绝变成
  一行 `runtime_event_append_failed` 写到 stdout。日志器把这些行按诊断限流为每分钟至多
  一条，覆盖 Redis 快速拒绝以及所有 event store 实现。限流器最多单独跟踪 32 种活跃诊断，
  超出的诊断共享一个 overflow 桶，避免攻击者可控的错误文本反过来让限流器自身的内存或
  输出无界；但丢弃路径仍不该让每个调用方各自处理同一个依赖故障。改为聚合上报：每次丢弃
  都进计数器，另有一行按原因限流（每原因每分钟至多一条）的丢弃日志（#268）。
- **上限不会放行这条链。** 它只是把存储切到丢弃模式；这一环本身仍然等待真正的答复。
  放行会让第二条写入落到一个两次都没回应过的连接上，并且在 Redis 恢复时乱序落库——而
  顺序正是这条链存在的理由。
- **读取不该排在它想读的那批写入后面；过了某个点更不该发出。** 这条链是串行的，所以
  `await pendingAppend` 会让一次读取依次等完每一条排队写入的**发出**与应答——那些往返
  甚至还没开始。给这段等待加界之后，读取只排在唯一那条在途写入后面。但只要那条写入
  不回应，读取同样回不来，而"等久一点"根本就是拿错了杠杆：后台事件页与
  概览页都每 15s 自动刷新，于是只要僵死还在，每一次轮询就往 ioredis 队列里再留下一条
  读和一个闭包——正是本节要消灭的那种、由定时器驱动的增长（#266 复审）。所以读取是被
  **拒绝**（`503 event_store_unavailable`），不是被延后。无界队列的解法，从来不是给
  "等它多久"加一道界。
- **"队列排空了没有"不是读取要回答的那个问题。** 第一版有界实现等完这条链之后，不管
  等到的是什么都照样发出读取，只有在 append 上限触发后才拒绝——而那是 5 秒之后，因为
  这个上限本就故意设得长（触发一次要丢记录）。这中间的每一次读取都排到了一条永远不会
  回来的命令后面，于是这道界本要消灭的缺陷原封不动地活了下来（#269 复审）。而且，一个
  仅仅是落后的 Redis，队列同样排不空，按这个答案去拒绝会在 Redis 正常工作时把控制台
  弄下线。真正的问题是连接**在不在回应**，能回答它的只有队首那条命令——而且是在**读取
  自己**的预算内，不是上限的预算内。两种行为，两个常量，又一次。
- **一条超时的读取，和一条超过上限的写入，是同一种证据，必须同样被记住。** 这道界的
  第一版答复了调用方却忘掉了那条命令。在 append 安静——或者正在被丢弃——的节点上，
  队首检查根本没有在途命令可看，于是下一次轮询畅通无阻地又排进一条读取，本节要消灭的
  "每轮一次"的增长在读取这一侧原样重现（#269 复审）。超时不是一条命令的终点，而是
  "已经知道这条连接坏了"的起点。用计数而不是布尔，因为写入链是串行的、读取却可以同时
  有好几条在途；而且命令最终应答时要释放，否则一次短暂的慢就会把后台页面按住直到进程
  重启。
- **那道检查是关于过去的证据，所以读取还需要它自己的一道界。** 读取排在它被**发出**的
  那一刻连接上的东西后面，而"检查之后、命令之前"才开始的僵死，任何发出前的检查都看
  不见。在那里再验一次队首既补不上这个缝，又会毁掉这条路径要保护的场景——有队列的节点
  上，队首几乎总是几毫秒前发出、尚未应答的写入，要求队首已应答等于在一个仅仅是落后的
  Redis 上拒绝每一次读取。于是两道界分工，且互不替代：队首检查挡住"僵死期间每轮轮询都
  发一次读取"，读取自身的命令超时挡住"僵死开始时已在途的那一次读取"一直等到 Node 默认
  的 300s `requestTimeout`（#269 复审）。代价是僵死起点漏出**一次**被拒绝的读取——下一
  次轮询会发现连接没有应答，发出任何命令之前就会被拒绝。
- **`close` 先有界排空，然后直接断开 socket——`QUIT` 不是逃生口。** 直接丢掉队列会在
  每次正常重启时丢掉关服自身的事件；无界等待则会在每次僵死关服时把这一步判为失败。
  event store 是日志器的汇，所以它的关服步骤排在所有共享生产者之后；提前关闭会静默丢掉
  它们的收尾事件。`close` 开始后仍到达的 append 会计入 abandonment 报告的
  `closingAppends`。关服步骤超时只答复调用方，并不会取消真实生产者；所以如果 append 在
  event store 步骤返回后才到达，会再发一条累计更新，而不是越过一次性的最终回调后无声
  消失。然后：在预算内等这条链，超出预算后让还没开始的环停下——连接即将消失，此后发出
  的命令会被拒绝，而日志器会在关服后生成受限流的
  `runtime_event_append_failed`。然后是 `disconnect()` 而**不是** `quit()`：ioredis 把
  `QUIT` 和其他命令放进同一个 `commandQueue`，应答从队首依次配对，所以优雅关闭会原样
  继承刚刚被限住的那段等待（#264 复审）。链排空时仍走优雅路径，但同样有界——半开的
  socket 会在没有写入可归咎时吞掉 `QUIT` 的应答；而这道界与这里的其他每一道一样欠一行
  上报（#266 复审）：它刚刚花掉了整个预算，而一个干净返回的 `close` 是它与"被记成成功
  关服"之间唯一的东西。`settleWithin` 回答的是"落定了没有"——这对排空是对的（被拒绝的
  写入也是一个答复），对 `QUIT` 是错的（一次拒绝落定得很干净，却把 socket 留在没人检查
  过的状态），所以那里是三种结局而不是两种。只做有界而不上报，与
  [后台轮次](#不能超时的后台轮次也就无法被观测)那条是同一个反向取舍，因此有
  `runtime_event_appends_abandoned_at_shutdown`。

一条连接，应答按顺序。这既是"只有 `disconnect` 才是有界关闭"的原因，也是那道读取拒绝
的推导来源。它同样是那道拒绝的边界：存储只能依据**自己**某条命令给出的证据去拒绝，
所以进入僵死后的**第一个**请求——无论它是读是写——都不会被拒绝。它会被有界地判为不可用
并答复调用方，然后它自己成为拒绝下一个请求的证据。这已是调用方一侧的界能做到的极限；
要彻底补上，需要独立的读连接或 `commandTimeout`。要补上这一段，需要独立的读连接或 `commandTimeout`——与 #261、#263 里被
推迟的是同一个决定，三处应当一起评估。这个存储的测试夹具只有模拟了这种顺序才值得信：让每次调用各自独立完成
的夹具，会乐于"证明"读取和关服能绕过一条僵死的写入。

## "哪条记录可以丢"是记录的属性，不是队列的属性

`redis-audit-store` 有一条和 event store 逐个环节一模一样的链，后果也一模一样
（#267）。它唯一不能照搬的是答案：审计记录是全系统唯一说得清"房间是谁关的、成员是谁
踢的"的东西，静默丢弃不是任何人可以替运维做的取舍。由此得到的规则：

- **抽出机制，把策略留在调用点。** 四道边界现在是 `admin/append-chain.ts`，两个存储
  的差别只在 `onRefused` / `onAbandonedAtShutdown` 两个回调里——事件存储返回它自己
  构造的记录，审计存储抛出。手写第二份链，正是 #242 里造成 6 条重复意见的那个形状，
  其中一半是"修了 A、漏了同构的 B"。
- **让"丢弃"划算的是喂养速率，而这不是设计里的常量。** 事件存储不能拒绝，因为它的
  调用方是结构化日志器，一次拒绝就是一条日志一行 stdout 错误。审计链由管理动作按人的
  速度喂养，所以"一次拒绝一行日志"付得起——而且这行日志是
  `admin_audit_log_append_failed`，`action-service.writeAudit` 早在这一切之前就已经
  接住它了。
- **已有序列能回答的问题，不要再加一个计数器。** 事件存储需要
  `bili_syncplay_event_store_appends_dropped_total`，是因为它的丢弃本来无声。审计的
  拒绝并非如此：`metricsCollector.recordEvent` 在每次 `logEvent` 时都会执行，不受
  `LOG_LEVEL` 与采样影响，所以
  `bili_syncplay_events_total{event="admin_audit_log_append_failed"}` 已经无须任何
  新增面就回答了"还在不在发生"和"发生了多少"。
- **管理动作照样成功，正因如此这次丢失必须够响。** 审计写入一直是发后不理的；在
  Redis 故障期间把管理能力一并下线是更坏的失败。既然动作无论如何都会发生，那么"丢了
  一条问责记录"和"没人知道"之间，就只剩下"拒绝是否可见"这一道。
- **关服步骤的预算属于步骤，不属于步骤里的某个组件。** `close_admin_services` 关的是
  管理会话存储**和**审计存储，而会话存储那句 `await redis.quit()` 原本也是无界的——
  只修审计存储的话，同一个 Redis 照样会让这一步失败。两个关闭现在一起 settle，而不是
  顺序 await，所以其中一个抛出不会跳过另一个的关闭。现在所有有界的 Redis 关闭都共用
  `quitWithin`；策略与预算仍留在各自调用点。

另外四个 Redis 设施也遵守同一规则（#270）：

- `redis-room-store`、`redis-admin-command-bus`、`redis-room-event-bus` 各自独占默认
  5s 关服步骤。它们给 `QUIT` 4s，给关服调度与降级上报留下 1s。两个总线通过
  `quitAllWithin` 并发关闭 publisher 与 subscriber；其中的 `allSettled` 保证一端关闭
  出错不会藏掉另一端 socket 的结果。
- `redis-runtime-store` 独占 15s 的特殊步骤。最坏情况是：收束后的队列用 5s 等在途尝试
  和刻意不设超时的在线调用方，再用 5s 等所有越过调用方等待的 Redis 命令真正结束，
  最后用 4s 等 `QUIT`；合计 14s，同样留下 1s 余量。每条命令都在运行时存储的 Redis
  客户端边界登记（包括直接读取与 `MULTI.exec()`），所以调用方已超时或上游关服步骤已
  放弃等待，都不会让命令从关服上报中消失。
- 非 `ok` 结果会断开 socket，并发出对应设施的 `*_close_unfinished` 事件。总线的上报
  还带客户端角色；运行时存储只要仍有调用方、命令、或节拍器手里的 attempt，即使
  `QUIT` 自己成功也会上报，并带上**三**类数量与调用方 drain 预算。是三个，因为排空
  等的是两个互相盲区的判据：命令集会重查，抓得到排空期间新发的命令，但在同一个
  attempt 的两条命令之间读作空；节拍器那一份跨得过这些缝，却只快照一次。只等——或者
  只报——前者，就会出现 `pendingCommands: 0` 而全程沉默的关闭（#272 复审）。只有边界
  却没有这些行，只会把原先 `server_shutdown_step_failed` 的沉默下移一层。
- 总线的终态关闭不再追加第二条 `UNSUBSCRIBE`。consumer 的普通退订可能正是半开 socket
  已经不回答的命令；`QUIT` 本来也会退出订阅模式，直接进入它的边界才能保证强制断开
  兜底可达。关服以外的逐命令边界仍属于 #271 的连接级策略。

## 测试夹具不得把类型检查绕过去

每个包的 `test/**` 都在 `npm run typecheck` 范围内——否则一次漏改了某个测试调用点的签名变更会悄悄通过这道门，
并可能顺带掩盖掉那个漏掉的参数所造成的行为回归（`#210` / `#211`）。
各个包如何满足这一点，取决于它的 src 与 test 能不能共用一套编译器配置：

- `protocol`、`server`、`extension` 需要第二个 project，因为它们的测试需要 `node` 类型
  （以及 `server` 对 `bench/` 的引用），而 src 构建不能带上这些。它们的 `typecheck` 先跑 `tsconfig.json`，
  再跑 `tsconfig.test.json`。
- `admin-ui` 不需要第二个 project：它的 `tsconfig.json` 本就包含 `test`
  （其 src 是由 Vite 编译的浏览器代码，因此无需拆分）。

新增的包按适用的那一种来选——不要为了"和多数保持一致"而添一个不必要的 `tsconfig.test.json`。

保持夹具诚实，不要用类型断言绕过检查器：一个不再符合其类型的夹具，通常意味着类型动了
（字段被改名、被删除，或变成了必填），修改的位置就在夹具里。
以下三类断言尤其要避免，因为每一类都会重新打开这道门本想关上的缺口：

- 对夹具使用 `as unknown as <DomainType>` / `as never`（`RoomState`、`PlaybackState`、`Session`、`RoomStore`）——
  它压掉的正是你想看到的"缺少必填字段"错误。
- 用 `as T` 让桩满足一个无约束的 `<T>(…) => Promise<T>`。没有任何值能栖居于每一个 `T`，所以这个断言是无条件的。
- 让桩满足一个把若干组请求/响应塞进同一个全可选响应类型的契约。此时 `{}` 满足一切，也就什么都没检查——
  `#211` 曾经犯过一次这个错误才发现它。

当一个回调只服务于一组请求/响应时，就声明那一组。当它服务于多组时，把它拆成每组一个回调
（`sendPlaybackUpdate` / `requestRoomStateHydration`），而不是放宽响应类型。
当载荷确实无法建模、且无论如何都要在运行时用守卫收窄时，就声明 `Promise<unknown>`，交给守卫去收窄。
如果某个消费者只用到一个大接口的一部分，它的参数就应当如实写出来（`Pick<RoomStore, "countRooms">`）——
这样假实现根本不需要断言。

对于确实无法伪造的平台/库对象（`ws.WebSocket`、`chrome.tabs.Tab`、`HTMLVideoElement`、`IncomingMessage`），
`as unknown as T` 是可以的；优先写一个共用的构造函数，而不是在每个调用点各断言一次。
