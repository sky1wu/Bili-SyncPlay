## 1. 背景

当前仓库已经具备 protocol、server、extension 和 admin-ui 的单元/组件测试、服务端 WebSocket E2E、Redis 集成测试和轻量基准测试，但尚无真正启动浏览器并加载构建产物的端到端测试：

- 根脚本 `npm run test:e2e` 只调用 server workspace 的 `test/e2e-smoke.test.ts`；该测试用 Node WebSocket 客户端验证房间协议，不启动浏览器。
- `npm run test:e2e:smoke:plan` 只输出一份 Playwright 计划，不执行计划中的 popup、background 或 content 流程。
- GitHub Actions 的 `verify` job 构建 Chrome/Edge 与 Firefox 目标，但不加载扩展、不打开 Bilibili 页面，也不验证播放器行为。

因此，现有检查能证明各模块和协议在测试替身下工作，却不能证明以下生产形态链路在真实浏览器运行时中可用：

```text
popup → background → WebSocket server → background → content script → HTMLVideoElement
```

本需求用于补齐这一层，并把“覆盖所有用户操作”约束为可枚举、可审计和可持续维护的操作目录，而不是承诺穷举无限的操作排列。

## 2. 术语

| 术语             | 定义                                                                                                              |
| ---------------- | ----------------------------------------------------------------------------------------------------------------- |
| 确定性浏览器 E2E | 加载真实扩展构建产物、运行真实浏览器进程和真实服务端，但由测试夹具提供可控 Bilibili 页面、媒体和 API 响应的测试。 |
| Windows 实机测试 | 在专用 Windows 物理机或隔离 Windows VM 中运行浏览器；本项目优先复用“WSL 服务端 + Windows 浏览器”的现有测试台。    |
| 真实站点巡检     | 访问线上 `www.bilibili.com`，验证内容脚本仍可注入并识别真实播放器和 SPA 导航。                                    |
| 硬门禁           | 失败时阻止 PR 合并或发布。                                                                                        |
| 软门禁           | 失败时保留失败结论、产生告警和诊断材料，但不因第三方服务波动自动阻止合并。                                        |
| 操作覆盖         | 操作目录中的每个操作至少有正向、拒绝/错误或恢复场景，并验证用户可见结果。                                         |
| 状态转换覆盖     | 对房间、共享源、页面身份、连接和播放状态的关键转换建立断言。                                                      |

## 3. 目标

### 3.1 核心目标

- **REQ-G01**：每个涉及运行时代码的 PR 必须自动执行确定性浏览器 E2E，并以硬门禁运行。
- **REQ-G02**：测试必须使用生成 `extension/dist` 或 `extension/dist-firefox` 的同一生产构建链路，并加载其 run-scoped 不可变副本；不得用重新实现的假扩展替代，也不得让浏览器直接依赖会被并发构建改写的共享目录。
- **REQ-G03**：测试必须至少同时运行房主和成员两个隔离客户端，覆盖完整双向同步链路。
- **REQ-G04**：当前产品公开支持的用户操作必须进入带稳定 ID 的操作目录，且能从测试报告追溯到用例。
- **REQ-G05**：Chrome/Edge/Firefox 与真实 Bilibili 页面兼容性必须有独立巡检，不得把 Chromium 夹具测试的通过解释为所有浏览器和线上页面均已验证。
- **REQ-G06**：失败结果必须携带足够材料，使维护者无需在同一台机器上立即复现也能定位失败发生在哪一跳。
- **REQ-G07**：真实站点、真实账号、真实浏览器自动更新造成的外部波动不得污染确定性硬门禁。

### 3.2 成功标准

项目达到以下状态时，视为本能力建设完成：

1. 拟设为 PR required check 的完整确定性 Chromium P0/P1 与 admin-ui 真实客户端套件连续运行 100 次，测试基础设施自身导致的失败不超过 1 次；产品缺陷导致的真实失败不计为基础设施不稳定。
2. 第 5.1 节优先级表中的所有 P0、P1 操作均有自动化用例，且每条用例至少断言一个用户可见结果和一个跨端结果。
3. Chrome/Edge/Firefox 核心 smoke 与真实站点 canary 均有最近 24 小时内的可见结果；发布时必须有目标发布产物对应的结果。
4. 任一失败都能取得 Playwright trace 或对应浏览器驱动的等价诊断、截图、各上下文控制台日志、服务端日志以及场景元数据。
5. 仓库文档明确区分“确定性浏览器 E2E 通过”“Windows 实机通过”“真实 B 站通过”，不再以一个笼统的 `E2E passed` 代替三者。

## 4. 范围

### 4.1 用户角色

- 房主：创建房间、分享视频、驱动播放状态。
- 普通成员：加入/离开房间、跟随共享视频、发起被允许的播放操作。
- 管理员：登录管理后台、查看状态并执行房间治理操作。

### 4.2 浏览器与页面

浏览器范围与当前产品声明一致：

- Chromium 自动化基线，用于每个 PR 的确定性扩展 E2E。
- 当前稳定版 Chrome、Edge，用于 Windows 实机巡检。
- Firefox 121+ 的当前稳定版，用于 Firefox 构建和 event page 运行时巡检。

页面范围以 `extension/public/manifest.json` 的 `content_scripts.matches` 为准：

- `/video/*`
- `/bangumi/play/*`
- `/festival/*`
- `/list/watchlater*`
- `/medialist/play/watchlater*`

还必须覆盖多 P、festival 的 `bvid + cid` 身份、SPA 自动连播及从共享页面进入非共享页面的隔离语义。

### 4.3 不在范围内

- Safari 和移动端浏览器；它们目前就是产品非目标。
- 自动化 Bilibili 登录、验证码、风控绕过或账号注册。
- 视频内容、弹幕、广告、推荐算法和 CDN 可用性本身。
- 人耳对声音同步质量的主观判断；自动化只验证播放器状态和可量化时间差。
- 所有操作的无限排列、所有浏览器历史版本及所有网络故障组合。
- 以 UI 自动化替代现有单元、协议、Redis、多节点和负载测试。

## 5. 功能需求

### 5.1 用户操作优先级

本表是操作优先级的唯一权威输入；实施阶段的覆盖检查必须直接解析或等价复刻此映射，不得从场景名称猜测优先级。

| 优先级 | 含义                         | 需求 ID                                                                                        |
| ------ | ---------------------------- | ---------------------------------------------------------------------------------------------- |
| P0     | 每个运行时代码 PR 的核心门禁 | `REQ-F010`～`REQ-F014`、`REQ-F020`～`REQ-F023`、`REQ-F030`～`REQ-F031`                         |
| P1     | 确定性全量矩阵               | `REQ-F015`～`REQ-F017`、`REQ-F024`～`REQ-F028`、`REQ-F032`～`REQ-F037`、`REQ-F040`～`REQ-F044` |

`REQ-F001`～`REQ-F006` 是测试编排约束，`REQ-F050`～`REQ-F054` 是浏览器/环境矩阵约束；它们仍须逐条追踪，但不属于用户操作优先级表。

### 5.2 测试编排

- **REQ-F001**：测试运行器必须从仓库根目录通过一个稳定 npm 脚本启动，脚本负责构建前置产物、启动依赖、运行用例和清理资源。
- **REQ-F002**：每个测试场景必须使用唯一临时目录、唯一服务端端口和隔离浏览器 profile；不得读取或写入维护者的日常浏览器 profile。浏览器启动前必须把构建产物的默认服务端地址指向本次运行独占的回环 bootstrap sink，并把产物复制到本次 run 独占、启动后不可变的目录再加载；并发场景不得从会被其他构建删除或覆盖的 `extension/dist*` 直接运行。禁止新 profile 先尝试连接日常开发用的 `ws://localhost:8787` 或其他外部服务。
- **REQ-F003**：房主和成员必须运行在不同浏览器上下文中，`chrome.storage.session`、cookie、tab、service worker 和页面历史互不共享。
- **REQ-F004**：服务端必须从操作系统分配可用端口，并仅放行本次测试发现的扩展 Origin；不得为 Chromium 确定性测试打开缺失 Origin 的开发豁免。
- **REQ-F005**：测试必须通过用户可用入口设置服务端地址、创建/加入房间和分享视频。纯渲染/输入场景可用扩展页 URL 打开 popup；依赖活动 Bilibili tab 的分享、打开共享视频等场景必须用真实 action popup 或等价且不改变活动 tab 的浏览器入口。不得直接写入内部 store 来跳过行为路径。
- **REQ-F006**：用例完成后必须等待服务端、浏览器和临时媒体服务器真实退出；清理超时应使运行失败并保留诊断材料。

### 5.3 Popup 操作目录

- **REQ-F010**：保存合法及非法 `ws://` / `wss://` 服务端地址，并验证错误、调整值和重连行为。
- **REQ-F011**：创建房间、复制邀请串、使用按钮或 Enter 加入房间、显式离开房间。
- **REQ-F012**：在未入房时分享当前视频，覆盖确认创建和取消两条路径。
- **REQ-F013**：房间已有其他共享视频时，覆盖确认替换和取消替换两条路径。
- **REQ-F014**：打开共享视频，验证活动标签页导航到规范化共享 URL。
- **REQ-F015**：开关页内分享按钮，并验证设置跨 popup 重开和页面重载保持。
- **REQ-F016**：复制日志和邀请串时验证剪贴板文本，不只验证按钮样式。
- **REQ-F017**：连接中、房间操作 pending、非法邀请串和服务端拒绝场景必须验证控件禁用和错误反馈。

### 5.4 页面与播放操作目录

- **REQ-F020**：对每一种受支持页面，验证 content script 注入、视频身份解析、标题解析、页内分享按钮挂载和分享成功。
- **REQ-F021**：验证用户播放、暂停、seek 和修改永久倍速能从操作者传播到另一成员。
- **REQ-F022**：验证远端应用产生的 `play`、`pause`、`seeking`、`seeked`、`ratechange`、`waiting`、`stalled`、`canplay`、`playing`、`timeupdate` 和 `ended` 事件不会形成无界回声广播。
- **REQ-F023**：验证处于播放态时双方最终播放状态和倍速一致，位置误差进入统一 E2E 容差；暂停/seek 后使用更严格的静态位置容差。
- **REQ-F024**：验证跨视频共享会打开正确页面，并在 metadata/canplay 迟到时最终应用最新而非已被超越的房间快照。
- **REQ-F025**：验证共享者自动连播下一视频会更新房间共享源；非共享者不会抢占分享所有权。
- **REQ-F026**：验证成员主动浏览到非共享视频时“加载即暂停、允许随后手动本地播放”，且本地播放不回写房间。
- **REQ-F027**：验证页面前进/后退、SPA 导航、快速连续换片、多 P、festival 和稍后再看页面的视频身份不会回退到陈旧 URL。
- **REQ-F028**：页内 toast、分享按钮拖动、全屏挂载和设置 popover 至少各有一条浏览器级 smoke；精细布局仍由组件测试负责。

### 5.5 房间和连接生命周期

- **REQ-F030**：验证晚加入成员获得当前共享视频和经发送时刻补龄后的播放快照。
- **REQ-F031**：验证成员加入、离开、断线重连和显式离房；自动重连必须复用会话成员身份，显式离房不得复用。
- **REQ-F032**：验证 background service worker 被终止后能按当前设计恢复 popup、房间和消息处理能力。
- **REQ-F033**：验证浏览器离线/在线、服务端先断后恢复、tab 刷新和共享 tab 关闭后的恢复或用户可见失败。
- **REQ-F034**：验证两成员近同时操作时，最终状态遵循服务端权威规则，且旧 actor 的迟到快照不能覆盖新快照。
- **REQ-F035**：验证分享所有者离开、断线重连和新成员加入时，客户端最终看到的分享所有者与服务端完整房间态一致；首次归属重同步 `room_state_updated` 被事件总线拒收时，必须在没有后续房间操作或页面刷新的情况下依靠重试最终收敛。
- **REQ-F036**：浏览器完全退出后的行为必须符合当前 `chrome.storage.session` 语义：不声称自动恢复已关闭的浏览器会话。
- **REQ-F037**：验证 runtime index reaper 清理离线节点会话后，存活客户端最终移除幽灵成员并获得正确的分享所有者；首次清理通告 `room_state_updated` 被事件总线拒收、房间随后保持空闲且后续 sweep 已无法从 runtime index 重新发现该房间时，必须仅依靠保留记录的重试最终收敛。临时停用该重试轨迹时，此场景必须因客户端成员或所有者持续陈旧而失败。

### 5.6 管理后台

- **REQ-F040**：验证管理员登录、登录失败、会话过期和退出。
- **REQ-F041**：验证 overview、rooms、events、audit 和 config 页面加载、刷新、筛选、分页及错误重试。
- **REQ-F042**：验证关闭房间、提前过期、清空共享视频、踢出成员、断开会话和批量操作的确认、原因、成功及部分失败结果。
- **REQ-F043**：治理动作必须由真实扩展客户端观察结果，例如被踢客户端断开并显示错误；按当前实现，被“断开会话”的客户端必须清空当前房间上下文、停止自动重连并显示专用错误。只断言管理 API 返回成功不算完整 E2E。
- **REQ-F044**：不同管理角色的可见操作和服务端授权拒绝都必须覆盖。

### 5.7 跨浏览器与真实站点

- **REQ-F050**：Chrome/Edge 实机 smoke 至少覆盖构建产物加载、popup、双客户端建房/入房、分享及播放/暂停/seek。
- **REQ-F051**：Firefox smoke 必须加载 Firefox 专用构建，在不访问线上 Bilibili 的确定性页面夹具上验证 event page、随机 `moz-extension://<uuid>` Origin、`ws://localhost` 和核心同步流程。
- **REQ-F052**：真实站点 canary 至少访问普通视频、番剧和 festival 公开页面；需要登录的稍后再看场景仅在专用测试账号凭据可用时运行。
- **REQ-F053**：真实站点测试不得高频刷新、批量抓取或尝试绕过验证码；遭遇登录/风控/地区限制时应报告为外部阻塞，而非伪装为产品通过。
- **REQ-F054**：WSL 服务端 + Windows 浏览器场景必须保留，用于验证跨时钟域实现没有把服务端时间戳与本地时间戳直接相减。

## 6. 测试判定要求

- **REQ-O001**：核心断言优先使用用户可见 UI、浏览器可观察的 `HTMLVideoElement` 状态和公开管理 API；不得只读取 extension 内部 store 后宣布用户流程成功。
- **REQ-O002**：位置同步容差、等待上限和消息风暴上限必须在单一策略模块中定义，不得散落于用例。第一阶段技术 spike 必须以当前 reconcile 阈值和实机基线校准具体数值。
- **REQ-O003**：每个跨端操作至少验证发起端反馈、接收端结果和稳定窗口内没有反向污染三项中的两项；P0 播放同步必须三项全部验证。
- **REQ-O004**：失败后的自动重跑只可用于分类“可复现/偶发”，第一次失败仍必须保留并计入稳定性指标；不得以重跑变绿替换原失败结论。
- **REQ-O005**：回归用例在修复提交进入主干前必须证明其能在缺少修复时失败。实现时应使用安全的文件备份或独立 worktree 验证，不得破坏未提交修改。
- **REQ-O006**：涉及跨时钟的断言只能比较同一时钟上的差值或协议携带的时长；不得在测试 oracle 中重新引入服务端时间戳减本地时间戳。

## 7. 非功能需求

### 7.1 稳定性和耗时

- **REQ-N001**：PR 硬门禁的目标总耗时为 10 分钟以内；P0 smoke 应在 5 分钟以内给出结果。
- **REQ-N002**：确定性测试不得依赖线上 Bilibili、公共 WebSocket 服务、个人账号或浏览器商店。
- **REQ-N003**：用例不得使用固定 `sleep` 作为成功条件；等待必须绑定可观察事件、状态或带诊断信息的超时。
- **REQ-N004**：媒体夹具必须短小、来源明确、可在仓库许可证下使用，且能稳定产生 play/pause/seek/rate/buffering/ended 信号。

### 7.2 可诊断性

- **REQ-N010**：失败 artifact 必须包含场景 ID、commit SHA、浏览器及版本、操作系统、扩展 ID/Origin、服务端端口、随机种子和各步骤起止时间。
- **REQ-N011**：保存每个浏览器上下文的遮罩截图、控制台/页面错误、service worker 或 event page 日志，以及服务端结构化日志；无凭据的 Playwright 上下文还须保存 trace，Firefox WebDriver lane 须保存 geckodriver/Marionette 日志和经过清洗的 WebDriver 命令/事件记录，并在 BiDi 能力可用且能证明已去除敏感头、cookie 和正文时保存网络事件或 HAR。场景只要会创建、复制、展示或输入邀请串、token、密码或 cookie，就必须在上下文启动前关闭原始 trace/HAR/网络正文，改用步骤日志、播放器采样、遮罩截图和服务端事件等价诊断，并在元数据中说明能力差异；不得依赖上传前丢弃已经捕获凭据的 trace，也不得伪造 `trace.zip`。
- **REQ-N012**：播放同步失败必须附带双方在同一采样周期的 URL、`currentTime`、`paused`、`readyState`、`playbackRate` 和本地单调采样值。
- **REQ-N013**：清理失败、浏览器崩溃和 artifact 上传失败本身都必须使对应 job 明确失败。
- **REQ-N014**：所有待上传文件都必须经过 allowlist 和 archive-aware 敏感信息扫描；扫描器至少使用本次运行登记的 token、cookie、密码、邀请串及通用 `Authorization`/`Cookie` 模式检查文本、解包后的 trace/HAR/归档内容和元数据。截图必须在采集时遮罩敏感区域。无法可靠清洗或扫描的非结构化产物不得上传，并须以无敏感数据的失败摘要替代；扫描失败本身使 job 失败。

### 7.3 安全与隐私

- **REQ-N020**：公开仓库的外部 PR 不得直接在持久化 Windows 自托管 runner 上执行任意提交代码。
- **REQ-N021**：实机 job 只能运行可信分支、维护者批准的 SHA，或运行在任务后销毁的隔离 VM 中。
- **REQ-N022**：测试账号必须是专用低权限账号；cookie/token 由 Actions secret 或系统凭据库注入，不进入仓库、artifact 或日志。
- **REQ-N023**：测试不得复用维护者日常浏览器 profile、个人 Bilibili 账号或生产服务端凭据。
- **REQ-N024**：临时目录清理只能作用于本次运行创建并校验过的明确路径，禁止对用户目录或工作区根执行递归删除。

## 8. 触发与门禁策略

| 触发            | 环境                  | 套件                                               | 门禁                               |
| --------------- | --------------------- | -------------------------------------------------- | ---------------------------------- |
| Pull request    | GitHub 托管 Ubuntu    | 现有检查 + 确定性 Chromium 双客户端 + admin-ui E2E | 硬门禁                             |
| `main` push     | GitHub 托管 Ubuntu    | 与 PR 相同                                         | 硬门禁                             |
| 每日定时        | 受保护 Windows runner | Chrome、Edge、Firefox 核心实机 smoke               | 硬门禁并告警；不追溯阻断已合并提交 |
| 每日定时        | 受保护 Windows runner | 真实 Bilibili canary                               | 软门禁；连续失败升级为人工检查     |
| 发布候选/tag 前 | 受保护 runner         | 发布产物、全浏览器核心矩阵、真实站点 canary        | 发布门禁；外部站点阻塞须人工确认   |

文档、翻译或纯元数据改动可以通过路径分类跳过浏览器 E2E，但修改分类规则本身必须受测试保护；`extension/`、`server/`、`packages/protocol/`、`packages/admin-ui/`、测试夹具、构建脚本和相关 workflow 的改动不得跳过。

## 9. 需求追踪

实施阶段必须维护机器可读或 Markdown 形式的追踪表，至少包含：

```text
需求 ID → 场景 ID → 自动化层 → 浏览器/页面矩阵 → 最近结果 → 负责人
```

一个需求可以由多个场景覆盖；一个场景也可以覆盖多个需求，但不得用“被其他测试间接覆盖”而没有明确断言的方式关闭需求。

追踪不能只读取场景的静态 tag。共享断言 helper 必须在执行时输出 `requirementId`、断言类别（发起端用户可见、接收端/服务端跨端结果、稳定窗口）、结果和时间；覆盖检查只认可本次测试报告中实际执行且通过的证据。空测试、跳过断言或只声明 requirement ID 均不得计为覆盖。
