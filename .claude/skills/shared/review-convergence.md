# 结构性修复与评审收敛（共享规则）

`fix-issue`、`add-feature` 和 `review-round` 共同使用本文件。这里只定义防止修复失控的
决策规则；不要为执行这些规则再增加账本、状态机、脚本或协议。

## 1. 写代码前先证明决策依据

缺陷修复和评审发现要为每个独立因果问题写下稳定的 `Root ID`，并回答：

1. 错误事实第一次在哪里产生，而不是最后在哪里显现？
2. 被破坏的不变量是什么？
3. 哪条调用链、日志或最小复现证明这个判断？
4. 正确决策需要什么信息，哪一层实际拥有它？
5. 什么最小实验能推翻当前假设？

纯新功能没有错误根因；改为写下稳定的 `Decision ID`，并回答：用户要得到什么结果、边界与
非目标是什么、设计依赖哪些假设、正确决策所需信息由哪一层拥有，以及什么验收证据会证明
设计成立或应被推翻。

当前类型的问题缺一项就先调查，不写实现。缺陷修复默认落在错误事实首次产生且信息完备的层；本地问题若要
扩到协议、服务端、持久化或接收端，必须先证明原层信息不足。谁执行效果，谁就在同一同步
边界记录效果身份；timer、队列或 `await` 前的预测标记不能代替效果所有权。

## 2. 锁定范围并检查全部出口

编辑前列出本次允许修改的文件/包、架构层、新增状态和需要覆盖的效果出口。范围外发现只
记录，不顺手修；必须扩范围时，先说明原边界为什么错误以及新增验收项。

实现前审计同根路径：所有入口与出口、状态读写、reset/cleanup、错误路径，以及事件缺失、
重复、乱序和 timer/`await` ABA。每个出口标记“已覆盖”或“不适用及原因”。

出现任一信号就停止当前编辑，重新画所有权、生命周期和全部出口：

- 在已有 suppression flag、cooldown 或特例上再加一个同生命周期机制。
- 一个局部 bug 扩到三个及以上架构层，却没有原层信息不足的证据。
- 发送端、接收端和持久化层分别补偿同一成因。
- 新状态没有唯一拥有者、明确清理点或反向对照测试。

## 3. 复审预算与停止条件

用当前任务记录和 PR 已有评审线程判断 `Root ID` 是否重复；不要另建机器可读账本，也不要
用评论数、finding 数下降或“补丁更小”冒充收敛。

- 第一次出现某根因：修正首次产生错误事实的位置，并审计全部同根出口。
- 第二次仍是同一根因：停止逐条补评论，撤回未发布的同根临时机制，重新设计所有权和
  生命周期；只允许一次结构性重做。
- 结构性重做后仍有同根意见，或层数/状态数继续增长：停止自动修改和自动复审，报告根因、
  当前设计为何不成立、已验证事实和剩余风险，交由用户决定是否扩大或缩小范围。

同一变更单元最多运行两次独立语义检视：Codex review、以 reviewer 身份进行的子代理审计和
独立人工复核都计入同一预算；跟进验证前一次意见也算新的一次。根因调查、回归验证和主代理按既定
出口清单执行的最终产品审计不计入。第二次仍有意见时，不再启动任何第三方检视；仅依据已有
证据在原范围内完成必要修正、有界的最终产品审计和完整门禁，并明确报告独立检视未达到无意见。
新根因也不能借机突破已锁定范围。

## 4. 命令与验证边界

- 切分支或编辑前拒绝脏工作树；需要时从目标 SHA 建独立干净 worktree，不携带、stash、
  提交或覆盖用户已有改动。
- 未经白名单验证的用户输入永远不能插入 shell 源码。编号先验证为纯数字；slug 先在 shell
  外派生并确认只含 `[a-z0-9-]`，再作为数据传入命令。
- 每个 fenced 命令块按新 shell 处理；块内重新取得所需值，多步命令用 `set -e` 或 `&&`。
- 只复审已提交、完整门禁通过且工作树干净的最终产品。`codex review` 必须独占一步并完整
  读取输出；退出码 0 不代表没有 finding，确认结果前禁止 push。
- 回归测试必须在只回退核心实现时因目标断言失败，反向对照仍通过。完成前运行仓库要求的
  完整门禁并报告实际结果。
